1: # A fresh Loops store for Atlas observations
2: 
3: This walkthrough uses `loops-min` to capture Atlas's photograph architecture
4: and keep evolving notes about it. You will create a credential binding and a
5: fresh Arrival store, declare two folds, append observations, and compare folded
6: state with the complete observation history.
7: 
8: The input is `~/Code/gruel.network/docs/atlas/architecture.json`, generated by
9: that project's architecture tooling. It describes **configured architecture**.
10: It includes source selectors and explicit unknowns; it does not establish live
11: health. This walkthrough reads that file and writes a separate scratch store.
12: It does not connect the Atlas browser to Loops or migrate an existing store.
13: 
14: The commands use the `arrival/finish` implementation at checkpoint `d4e5792d`.
15: Prerequisites: Python 3.11+, `uv`, and the two local checkouts. Copy the **six
16: Bash blocks below, in order, into one script**, such as `atlas-quickstart.sh`,
17: then run it with `bash atlas-quickstart.sh`. Later steps use variables and
18: functions established by earlier steps. This script execution is the tested
19: path; do not paste the strict shell options into your interactive shell.
20: Start a fresh scratch directory for each run rather than repeating writes
21: into an earlier run.
22: 
23: ## 1. Prepare an isolated workspace
24: 
25: Adjust `LOOPS_CHECKOUT` if your Arrival checkout is elsewhere. The virtual
26: environment, credentials, witness state, projections, and command receipts all
27: live under `ATLAS_WORK`. Its path is printed so you can inspect it afterward.
28: `uv sync` may resolve dependencies and update the Loops checkout's ignored
29: `uv.lock`; the environment it installs into is isolated under `ATLAS_WORK`.
30: 
31: ```bash
32: set -euo pipefail
33: umask 077
34: export LOOPS_CHECKOUT="$HOME/Code/loops-wt/arrival-finish"
35: cd "$HOME/Code/gruel.network/docs/atlas"
36: test -f architecture.json
37: export ATLAS_WORK="$(mktemp -d "${TMPDIR:-/tmp}/atlas-loops.XXXXXX")"
38: export UV_PROJECT_ENVIRONMENT="$ATLAS_WORK/venv"
39: export XDG_STATE_HOME="$ATLAS_WORK/state"
40: export XDG_CONFIG_HOME="$ATLAS_WORK/config"
41: export LOOPS_HOME="$ATLAS_WORK/loops-config"
42: export ATLAS_KEYS="$ATLAS_WORK/credentials"
43: export ATLAS_VERTEX="$ATLAS_WORK/atlas.vertex"
44: 
45: uv sync --project "$LOOPS_CHECKOUT" --package loops-min --no-dev
46: export LOOPS_MIN="$UV_PROJECT_ENVIRONMENT/bin/loops-min"
47: cp architecture.json "$ATLAS_WORK/architecture.json"
48: printf 'Workspace: %s\n' "$ATLAS_WORK"
49: ```
50: 
51: Use `loops-min`, the new JSON CLI. The legacy `loops` executable is a different
52: application. Each successful command below returns an envelope with `ok: true`
53: and an SDK-owned `result`; saved JSON files retain that evidence.
54: 
55: ## 2. Choose an observer and initialize
56: 
57: `atlas-guide` is the observer authoring these example observations.
58: `atlas-demo` is the namespace for its **local credential binding**.
59: `atlas-notes` is the vertex's name. These names serve different purposes; none
60: is inferred from `atlas.vertex`.
61: 
62: The binding token identifies this credential-creation operation. Creating a
63: binding alone does not authorize its observer in a store. Initialization uses
64: the binding to sign the new store's founding records and declaration.
65: 
66: ```bash
67: "$LOOPS_MIN" credential-create "$ATLAS_KEYS" \
68:   --namespace atlas-demo --observer atlas-guide --token atlas-guide-key-v1 \
69:   > "$ATLAS_WORK/binding.json"
70: 
71: atlas_write() {
72:   "$LOOPS_MIN" "$@" \
73:     --credential-root "$ATLAS_KEYS" \
74:     --credential-namespace atlas-demo --receipt-observer atlas-guide
75: }
76: 
77: atlas_write init "$ATLAS_VERTEX" --name atlas-notes \
78:   --location "$ATLAS_WORK/atlas.arrival" --observer atlas-guide --strict \
79:   > "$ATLAS_WORK/init.json"
80: "$LOOPS_MIN" inspect "$ATLAS_VERTEX" > "$ATLAS_WORK/inspect-initial.json"
81: ```
82: 
83: Fresh initialization creates and synchronizes the declaration history. There
84: is no separate adoption step. The initial scaffold contains an `item` kind;
85: the next step replaces that unused example with the kinds we want.
86: 
87: ## 3. Declare what the observations mean
88: 
89: We will keep one latest **whole graph** per scope in `atlas.snapshot`, and one
90: latest note per subject in `atlas.note`. A whole snapshot keeps source indices,
91: relationships, unknowns, and revision together; source index `16` in one
92: snapshot must not be interpreted using another snapshot's source list.
93: 
94: The `"by"` fold replaces the value for a matching payload key in folded state.
95: It does not replace old facts. Selection follows receipt order, not the largest
96: authored timestamp. With several observers, this particular note fold would
97: choose the last received note across them; use a different grouping or vertex
98: definition if you want their interpretations kept separately.
99: 
100: Create a proposal from the freshly generated scaffold, retaining its residence
101: and observer block. Apply it through the CLI so the declaration change is
102: recorded in the store.
103: 
104: ```bash
105: python3 - <<'PY'
106: import os
107: from pathlib import Path
108: 
109: work = Path(os.environ["ATLAS_WORK"])
110: text = Path(os.environ["ATLAS_VERTEX"]).read_text()
111: prefix, _ = text.split("\nloops {", 1)  # This walkthrough's fresh scaffold only.
112: proposal = prefix + '''
113: loops {
114:   atlas.snapshot {
115:     fold { snapshots "by" "scope" }
116:   }
117:   atlas.note {
118:     fold { notes "by" "subject" }
119:   }
120: }
121: '''
122: (work / "proposed.vertex").write_text(proposal)
123: PY
124: 
125: atlas_write declaration "$ATLAS_VERTEX" \
126:   --proposed-file "$ATLAS_WORK/proposed.vertex" --observer atlas-guide \
127:   > "$ATLAS_WORK/declaration.json"
128: ```

130: ## 4. Append the graph and a first note together
131: 
132: The batch below retains the copied graph, its revision, and a hash of the
133: exact input bytes. The note references that snapshot's fact ID and the photo
134: mount entity. Those payload references are application data, not automatic
135: foreign-key validation. The message preserves the graph's unresolved backing
136: claim; it does not infer a disk or network filesystem from a host path.
137: 
138: ```bash
139: python3 - <<'PY'
140: import hashlib
141: import json
142: import os
143: from pathlib import Path
144: 
145: work = Path(os.environ["ATLAS_WORK"])
146: raw = (work / "architecture.json").read_bytes()
147: graph = json.loads(raw)
148: assert graph["schema_version"] == 1
149: assert graph["scope"] == "photographs" and graph["state"] == "configured"
150: unknown = next(u for u in graph["unknowns"]
151:                if u["subject"] == "mount:immich-photos" and u["field"] == "backing")
152: snapshot_id = "atlas-snapshot-" + graph["revision"]
153: note = {
154:     "subject": unknown["subject"], "snapshot_fact_id": snapshot_id,
155:     "status": "question", "message": unknown["reason"],
156: }
157: batch = [
158:     {"id": snapshot_id, "kind": "atlas.snapshot", "observer": "atlas-guide",
159:      "origin": "docs/atlas/architecture.json",
160:      "payload": {"scope": graph["scope"], "graph": graph,
161:                  "input_sha256": hashlib.sha256(raw).hexdigest()}},
162:     {"id": "atlas-note-1", "kind": "atlas.note", "observer": "atlas-guide",
163:      "origin": "atlas-greenfield-guide", "payload": note},
164: ]
165: (work / "batch.json").write_text(json.dumps(batch))
166: note.update(status="follow-up",
167:             message="Inspect the family VM filesystem and mount source before naming the backing.")
168: (work / "follow-up.json").write_text(json.dumps(note))
169: PY
170: 
171: atlas_write emit-batch "$ATLAS_VERTEX" \
172:   --facts-json "$(cat "$ATLAS_WORK/batch.json")" > "$ATLAS_WORK/batch-receipt.json"
173: "$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.note \
174:   > "$ATLAS_WORK/notes-before.json"
175: ```
176: 
177: The example is a small batch passed as a command argument. A large estate or
178: continuous importer needs an SDK-based ingestion path; this CLI does not yet
179: provide a source runner or streaming import command.
180: 
181: ## 5. Append a follow-up and compare views
182: 
183: The follow-up is an example of an observer's intended investigation. It makes
184: no new claim about actual storage backing. It uses a new fact ID and the same
185: subject, so the note fold advances while both notes remain available.
186: 
187: ```bash
188: atlas_write emit "$ATLAS_VERTEX" atlas.note --observer atlas-guide \
189:   --origin atlas-greenfield-guide --id atlas-note-2 \
190:   --payload-json "$(cat "$ATLAS_WORK/follow-up.json")" \
191:   > "$ATLAS_WORK/follow-up-receipt.json"
192: 
193: "$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.note \
194:   > "$ATLAS_WORK/notes-after.json"
195: "$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.snapshot \
196:   > "$ATLAS_WORK/snapshot-state.json"
197: "$LOOPS_MIN" facts "$ATLAS_VERTEX" --kind atlas.note --order oldest --limit 10 \
198:   > "$ATLAS_WORK/note-history.json"
199: 
200: python3 - <<'PY'
201: import json
202: import os
203: from pathlib import Path
204: 
205: work = Path(os.environ["ATLAS_WORK"])
206: def result(name):
207:     envelope = json.loads((work / name).read_text())
208:     assert envelope["ok"] is True
209:     return envelope["result"]
210: 
211: subject = "mount:immich-photos"
212: before = result("notes-before.json")["sections"]["atlas.note"]["notes"][subject]
213: after = result("notes-after.json")["sections"]["atlas.note"]["notes"][subject]
214: history = result("note-history.json")
215: assert before["status"] == "question" and after["status"] == "follow-up"
216: assert history["truncated"] is False
217: assert [fact["id"] for fact in history["items"]] == ["atlas-note-1", "atlas-note-2"]
218: snapshot = result("snapshot-state.json")["sections"]["atlas.snapshot"]["snapshots"]["photographs"]
219: assert snapshot["graph"] == json.loads((work / "architecture.json").read_text())
220: print("Latest note:", after["message"])
221: print("History:", len(history["items"]), "notes; captured graph preserved intact")
222: PY
223: ```
224: 
225: `state` is the interpretation chosen by the declaration. `facts` is the
226: underlying history. Here, changing what you see required appending an
227: observation; the earlier observation and captured configuration remain intact.
228: 
229: ## 6. Inspect, verify, and capture the prefix
230: 
231: Ordinary successful writers synchronize their projection. `sync` below checks
232: that boundary explicitly; inspect its actual result instead of assuming that
233: every successful append necessarily completed all later work.
234: 
235: ```bash
236: "$LOOPS_MIN" inspect "$ATLAS_VERTEX" > "$ATLAS_WORK/inspect-final.json"
237: "$LOOPS_MIN" verify "$ATLAS_VERTEX" > "$ATLAS_WORK/verify.json"
238: "$LOOPS_MIN" sync "$ATLAS_VERTEX" > "$ATLAS_WORK/sync.json"
239: "$LOOPS_MIN" export "$ATLAS_VERTEX" "$ATLAS_WORK/captured.jsonl" \
240:   > "$ATLAS_WORK/export.json"
241: printf 'Receipts, declaration, store, and captured prefix: %s\n' "$ATLAS_WORK"
242: ```
243: 
244: `inspect` compares the local declaration with effective declaration history. `verify`
245: reports grammar, density, lineage, and hash-chain claims; it does not establish
246: signature authorship, external key trust, or projection agreement. `sync`
247: reports the captured and projected heads. Result fields vary by operation:
248: `emit` supplies `signed`, `witnessed`, and `commit`; `emit-batch` supplies a
249: shared commit plus per-item signed/witnessed/stored evidence. Initialization
250: reports a head and phase; for declaration editing, inspect `status` and the
251: commit's `before`/`after` heads. Selecting mapped credentials alone is not a
252: universal mandatory-signing policy.
253: 
254: The export is a captured wire prefix at a new pathname. It is not a standalone
255: backup of credentials, local witnesses, and descriptor, and the CLI does not
256: yet provide empty-receiver import. Keep this scratch workspace if you want to
257: inspect or continue it; a durable project store should use deliberate stable
258: locations and a planned credential/witness backup policy.

260: ## If a command is interrupted
261: 
262: The guide stops on a nonzero exit. Retain stdout JSON, stderr, the binding
263: token, and any returned intent/commit evidence. Exit 6 means ledger custody
264: committed or may have committed, or a credential mutation is incomplete. Do not
265: blindly repeat the operation. Stable fact
266: IDs help identify the operation but are not a blanket retry guarantee.
267: 
268: Recovery commands, when the corresponding retained intent warrants them:
269: 
270: ```text
271: loops-min credential-recover ROOT --namespace atlas-demo --observer atlas-guide --token atlas-guide-key-v1
272: loops-min init-recover TARGET
273: loops-min declaration-recover INTENT
274: ```
275: 
276: Recovery uses the reserved operation's evidence. It does not choose a new
277: observer, lineage, or signatures. Successful initialization removes its intent;
278: running `init-recover` after normal success is not a health check.
