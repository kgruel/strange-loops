# A fresh Loops store for Atlas observations

This walkthrough uses `loops-min` to capture Atlas's photograph architecture
and keep evolving notes about it. You will create a credential binding and a
fresh Arrival store, declare two folds, append observations, and compare folded
state with the complete observation history.

The input is `~/Code/gruel.network/docs/atlas/architecture.json`, generated by
that project's architecture tooling. It describes **configured architecture**.
It includes source selectors and explicit unknowns; it does not establish live
health. This walkthrough reads that file and writes a separate scratch store.
It does not connect the Atlas browser to Loops or migrate an existing store.

The commands use the `arrival/finish` implementation at checkpoint `d4e5792d`.
Prerequisites: Python 3.11+, `uv`, and the two local checkouts. Copy the **six
Bash blocks below, in order, into one script**, such as `atlas-quickstart.sh`,
then run it with `bash atlas-quickstart.sh`. Later steps use variables and
functions established by earlier steps. This script execution is the tested
path; do not paste the strict shell options into your interactive shell.
Start a fresh scratch directory for each run rather than repeating writes
into an earlier run.

## 1. Prepare an isolated workspace

Adjust `LOOPS_CHECKOUT` if your Arrival checkout is elsewhere. The virtual
environment, credentials, witness state, projections, and command receipts all
live under `ATLAS_WORK`. Its path is printed so you can inspect it afterward.
`uv sync` may resolve dependencies and update the Loops checkout's ignored
`uv.lock`; the environment it installs into is isolated under `ATLAS_WORK`.

```bash
set -euo pipefail
umask 077
export LOOPS_CHECKOUT="$HOME/Code/loops-wt/arrival-finish"
cd "$HOME/Code/gruel.network/docs/atlas"
test -f architecture.json
export ATLAS_WORK="$(mktemp -d "${TMPDIR:-/tmp}/atlas-loops.XXXXXX")"
export UV_PROJECT_ENVIRONMENT="$ATLAS_WORK/venv"
export XDG_STATE_HOME="$ATLAS_WORK/state"
export XDG_CONFIG_HOME="$ATLAS_WORK/config"
export LOOPS_HOME="$ATLAS_WORK/loops-config"
export ATLAS_KEYS="$ATLAS_WORK/credentials"
export ATLAS_VERTEX="$ATLAS_WORK/atlas.vertex"

uv sync --project "$LOOPS_CHECKOUT" --package loops-min --no-dev
export LOOPS_MIN="$UV_PROJECT_ENVIRONMENT/bin/loops-min"
cp architecture.json "$ATLAS_WORK/architecture.json"
printf 'Workspace: %s\n' "$ATLAS_WORK"
```

This guide installs the workspace `loops-min` package with `--package loops-min`
and invokes that explicit binary; it does not install or exercise root-wheel
aliases. In a newly installed root wheel, `sl`, `loops`, and `loops-min` share
the JSON client, while the standalone workspace `apps/loops` entry point can
still be legacy. Each successful command below returns an envelope with
`ok: true` and an SDK-owned `result`; saved JSON files retain that evidence.

## 2. Choose an observer and initialize

`atlas-guide` is the observer authoring these example observations.
`atlas-demo` is the namespace for its **local credential binding**.
`atlas-notes` is the vertex's name. These names serve different purposes; none
is inferred from `atlas.vertex`.

The binding token identifies this credential-creation operation. Creating a
binding alone does not authorize its observer in a store. Initialization uses
the binding to sign the new store's founding records and declaration.

```bash
"$LOOPS_MIN" credential-create "$ATLAS_KEYS" \
  --namespace atlas-demo --observer atlas-guide --token atlas-guide-key-v1 \
  > "$ATLAS_WORK/binding.json"

atlas_write() {
  "$LOOPS_MIN" "$@" \
    --credential-root "$ATLAS_KEYS" \
    --credential-namespace atlas-demo --receipt-observer atlas-guide
}

atlas_write init "$ATLAS_VERTEX" --name atlas-notes \
  --location "$ATLAS_WORK/atlas.arrival" --observer atlas-guide --strict \
  > "$ATLAS_WORK/init.json"
"$LOOPS_MIN" inspect "$ATLAS_VERTEX" > "$ATLAS_WORK/inspect-initial.json"
```

Fresh initialization creates and synchronizes the declaration history. There
is no separate adoption step. The initial scaffold contains an `item` kind;
the next step replaces that unused example with the kinds we want.

## 3. Declare what the observations mean

We will keep one latest **whole graph** per scope in `atlas.snapshot`, and one
latest note per subject in `atlas.note`. A whole snapshot keeps source indices,
relationships, unknowns, and revision together; source index `16` in one
snapshot must not be interpreted using another snapshot's source list.

The `"by"` fold replaces the value for a matching payload key in folded state.
It does not replace old facts. Selection follows receipt order, not the largest
authored timestamp. With several observers, this particular note fold would
choose the last received note across them; use a different grouping or vertex
definition if you want their interpretations kept separately.

Create a proposal from the freshly generated scaffold, retaining its residence
and observer block. Apply it through the CLI so the declaration change is
recorded in the store.

```bash
python3 - <<'PY'
import os
from pathlib import Path

work = Path(os.environ["ATLAS_WORK"])
text = Path(os.environ["ATLAS_VERTEX"]).read_text()
prefix, _ = text.split("\nloops {", 1)  # This walkthrough's fresh scaffold only.
proposal = prefix + '''
loops {
  atlas.snapshot {
    fold { snapshots "by" "scope" }
  }
  atlas.note {
    fold { notes "by" "subject" }
  }
}
'''
(work / "proposed.vertex").write_text(proposal)
PY

atlas_write declaration "$ATLAS_VERTEX" \
  --proposed-file "$ATLAS_WORK/proposed.vertex" --observer atlas-guide \
  > "$ATLAS_WORK/declaration.json"
```

## 4. Append the graph and a first note together

The batch below retains the copied graph, its revision, and a hash of the
exact input bytes. The note references that snapshot's fact ID and the photo
mount entity. Those payload references are application data, not automatic
foreign-key validation. The message preserves the graph's unresolved backing
claim; it does not infer a disk or network filesystem from a host path.

```bash
python3 - <<'PY'
import hashlib
import json
import os
from pathlib import Path

work = Path(os.environ["ATLAS_WORK"])
raw = (work / "architecture.json").read_bytes()
graph = json.loads(raw)
assert graph["schema_version"] == 1
assert graph["scope"] == "photographs" and graph["state"] == "configured"
unknown = next(u for u in graph["unknowns"]
               if u["subject"] == "mount:immich-photos" and u["field"] == "backing")
snapshot_id = "atlas-snapshot-" + graph["revision"]
note = {
    "subject": unknown["subject"], "snapshot_fact_id": snapshot_id,
    "status": "question", "message": unknown["reason"],
}
batch = [
    {"id": snapshot_id, "kind": "atlas.snapshot", "observer": "atlas-guide",
     "origin": "docs/atlas/architecture.json",
     "payload": {"scope": graph["scope"], "graph": graph,
                 "input_sha256": hashlib.sha256(raw).hexdigest()}},
    {"id": "atlas-note-1", "kind": "atlas.note", "observer": "atlas-guide",
     "origin": "atlas-greenfield-guide", "payload": note},
]
(work / "batch.json").write_text(json.dumps(batch))
note.update(status="follow-up",
            message="Inspect the family VM filesystem and mount source before naming the backing.")
(work / "follow-up.json").write_text(json.dumps(note))
PY

atlas_write emit-batch "$ATLAS_VERTEX" \
  --facts-json "$(cat "$ATLAS_WORK/batch.json")" > "$ATLAS_WORK/batch-receipt.json"
"$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.note \
  > "$ATLAS_WORK/notes-before.json"
```

The example is a small batch passed as a command argument. A large estate or
continuous importer needs an SDK-based ingestion path; this CLI does not yet
provide a source runner or streaming import command.

## 5. Append a follow-up and compare views

The follow-up is an example of an observer's intended investigation. It makes
no new claim about actual storage backing. It uses a new fact ID and the same
subject, so the note fold advances while both notes remain available.

```bash
atlas_write emit "$ATLAS_VERTEX" atlas.note --observer atlas-guide \
  --origin atlas-greenfield-guide --id atlas-note-2 \
  --payload-json "$(cat "$ATLAS_WORK/follow-up.json")" \
  > "$ATLAS_WORK/follow-up-receipt.json"

"$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.note \
  > "$ATLAS_WORK/notes-after.json"
"$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.snapshot \
  > "$ATLAS_WORK/snapshot-state.json"
"$LOOPS_MIN" facts "$ATLAS_VERTEX" --kind atlas.note --order oldest --limit 10 \
  > "$ATLAS_WORK/note-history.json"

python3 - <<'PY'
import json
import os
from pathlib import Path

work = Path(os.environ["ATLAS_WORK"])
def result(name):
    envelope = json.loads((work / name).read_text())
    assert envelope["ok"] is True
    return envelope["result"]

subject = "mount:immich-photos"
before = result("notes-before.json")["sections"]["atlas.note"]["notes"][subject]
after = result("notes-after.json")["sections"]["atlas.note"]["notes"][subject]
history = result("note-history.json")
assert before["status"] == "question" and after["status"] == "follow-up"
assert history["truncated"] is False
assert [fact["id"] for fact in history["items"]] == ["atlas-note-1", "atlas-note-2"]
snapshot = result("snapshot-state.json")["sections"]["atlas.snapshot"]["snapshots"]["photographs"]
assert snapshot["graph"] == json.loads((work / "architecture.json").read_text())
print("Latest note:", after["message"])
print("History:", len(history["items"]), "notes; captured graph preserved intact")
PY
```

`state` is the interpretation chosen by the declaration. `facts` is the
underlying history. Here, changing what you see required appending an
observation; the earlier observation and captured configuration remain intact.

## 6. Inspect, verify, and capture the prefix

Ordinary successful writers synchronize their projection. `sync` below checks
that boundary explicitly; inspect its actual result instead of assuming that
every successful append necessarily completed all later work.

```bash
"$LOOPS_MIN" inspect "$ATLAS_VERTEX" > "$ATLAS_WORK/inspect-final.json"
"$LOOPS_MIN" verify "$ATLAS_VERTEX" > "$ATLAS_WORK/verify.json"
"$LOOPS_MIN" sync "$ATLAS_VERTEX" > "$ATLAS_WORK/sync.json"
"$LOOPS_MIN" export "$ATLAS_VERTEX" "$ATLAS_WORK/captured.jsonl" \
  > "$ATLAS_WORK/export.json"
printf 'Receipts, declaration, store, and captured prefix: %s\n' "$ATLAS_WORK"
```

`inspect` compares the local declaration with effective declaration history. `verify`
reports grammar, density, lineage, and hash-chain claims; it does not establish
signature authorship, external key trust, or projection agreement. `sync`
reports the captured and projected heads. Result fields vary by operation:
`emit` supplies `signed`, `witnessed`, and `commit`; `emit-batch` supplies a
shared commit plus per-item signed/witnessed/stored evidence. Initialization
reports a head and phase; for declaration editing, inspect `status` and the
commit's `before`/`after` heads. Selecting mapped credentials alone is not a
universal mandatory-signing policy.

The export is a captured wire prefix at a new pathname. It is not a standalone
backup of credentials, local witnesses, and descriptor, and the CLI does not
yet provide empty-receiver import. Keep this scratch workspace if you want to
inspect or continue it; a durable project store should use deliberate stable
locations and a planned credential/witness backup policy.

## If a command is interrupted

The guide stops on a nonzero exit. Retain stdout JSON, stderr, the binding
token, and any returned intent/commit evidence. Exit 6 means ledger custody
committed or may have committed, or a credential mutation is incomplete. Do not
blindly repeat the operation. Stable fact
IDs help identify the operation but are not a blanket retry guarantee.

Recovery commands, when the corresponding retained intent warrants them:

```text
loops-min credential-recover ROOT --namespace atlas-demo --observer atlas-guide --token atlas-guide-key-v1
loops-min init-recover TARGET
loops-min declaration-recover INTENT
```

Recovery uses the reserved operation's evidence. It does not choose a new
observer, lineage, or signatures. Successful initialization removes its intent;
running `init-recover` after normal success is not a health check.

For command and outcome details, see the [minimal CLI reference](../../apps/loops-min/README.md).
