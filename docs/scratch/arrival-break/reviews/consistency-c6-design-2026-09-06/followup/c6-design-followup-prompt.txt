11: ## Decision and scope
12: 
13: A continuing boundary keeps its recorded consumption history. An ordinary
14: declaration edit changes the current interpretation of facts; it does not
15: restart that boundary. The proposed identity for this supported subset remains
16: the exact local vertex name, boundary role, and boundary name. No declaration
17: hash, file path, projection generation, or new wire identifier becomes identity.

19: The recommended policy is **inherit for in-place edits**. A trigger/count,
20: condition, fold, parse, route, or dispatch edit keeps the existing tick edge.
21: This is an explicit interpretation policy, not a claim that the old tick would
22: have fired under the new rules. A pending fact already consumed by that edge
23: does not become eligible again just because a declaration changed.
24: 
25: Whole-loop retirement followed by same-name recreation needs separate evidence
26: when an old local tick exists. A tick whose loop/vertex role was ambiguous when
27: received also cannot become unambiguous through a later configuration edit.
28: Those cases refuse runtime when the target consumes that ambiguous stream.
29: Removing the consumer is allowed; reintroducing it re-exposes the same conflict.

40: ## What the implementation actually does today
41: 
42: `Vertex.hydrate_snapshot` re-folds captured facts under the current declaration
43: in receipt order. It does **not** deserialize an old tick payload as current
44: fold state. A local loop tick invokes `Loop.replay_boundary`: reset to the
45: current initial state when reset is enabled, clear repeating-count bookkeeping,
46: or mark a one-shot boundary exhausted. A local vertex tick restores the vertex
47: period timestamp and does not reset every loop.
48: 
49: `plan_pending_boundaries` selects the greatest event-time/receipt edge per local
50: tick name. Facts at an equal timestamp precede or follow that edge by receipt
51: coordinate. This remains distinct from the tick's fact cursor and from
52: declaration receipt ordering. Count boundaries remain ingress-driven.
53: 
54: The grammar currently exposes `when`, `after`, and `every`; its compiler always
55: sets loop-boundary `reset=True`. The lower-level `Loop` supports carry, but
56: there is no public declaration reset/carry edit to implement in C6. Fold
57: overrides replace initial state and fold code, not declared boundary reset.
58: 
59: Consequently an in-place count edit retains the recorded boundary and replays
60: facts after it. The exact existing count-recovery behavior is:
61: 
62: | Target mode and retained evidence | Hydrated state and next behavior |
63: | --- | --- |
64: | `every M`, with an owned tick and K subsequently routed facts | Count is K, including when K >= M. Hydration does not fire. If K >= M, the next accepted routed ingress fires; otherwise M-K more routed facts are needed. |
65: | `every M`, with no owned tick and K replayed facts | Existing recovery sets count to K modulo M. It creates no missing historical ticks. |
66: | `after M`, with any owned loop tick | Inherits an exhausted one-shot boundary. New ingress does not restart it. |
67: | `after M`, with no owned tick and K replayed facts | Exhausted when K >= M; otherwise count is K. A fresh name can therefore already be exhausted by older facts. |
68: | `after` changed in place to `every M`, with an old owned tick | Current repeating mode resumes from that retained tick and subsequent routed facts, not from the declaration edit. |
69: | Kind-trigger edit with an owned tick | Pending evaluation retains the old event-time/receipt edge; only unconsumed facts are checked against the new trigger/conditions. |
70: 
71: A user wanting a fresh count or first firing is requesting a restart; C6 does
72: not silently provide one. Historical payloads keep their original meaning and
73: bytes even when current replay differs. Count-return values ignored during
74: hydration must not turn into retrospective dispatch or appended ticks.

104: ## History and evidence algorithm
105: 
106: The shared validator is pure over one captured declaration anchor, complete
107: self-lineage declaration fact history, bounded ticks, and the target document
108: set (effective current state for runtime, proposed successor for editing).
109: It does not open a store, sign, read keys, consult external source files or the
110: environment, repair projections, or execute any source/dispatch command.
111: 
112: 1. Validate the declaration anchor against the captured full H through the
113:    existing custody/projection contract. Select only the own genesis and
114:    self-lineage declaration overlays. Foreign and unscoped declarations remain
115:    inert, matching the existing resolver. Sort by receipt ordinal and sequence,
116:    never authored time or fact ID.
117: 2. Reconstruct effective runtime names at the genesis and each committed
118:    declaration revision. Preserve retirement evidence across intermediate
119:    revisions; do not compare only genesis/current or before/proposed documents.
120:    Multiple declaration documents in one Arrival batch form one revision:
121:    evaluate the resulting effective set, not transient partial document states
122:    with no observable runtime between them. This grouping is for namespace
123:    continuity; document overlay order remains receipt-sequence order. Wire
124:    batches contain fact rows only; a CAS containing fact and tick drafts gives
125:    those drafts distinct record ordinals. A query reporting an owned tick and
126:    declaration fact at the same ordinal contradicts this shape and refuses
127:    with both actual coordinates. Do not invent an ordering for that adapter
128:    contradiction. This is not a newly legal mixed-row record format.
129: 3. At each owned tick's receipt position, classify its role using that revision.
130:    A vertex-name tick with a simultaneously present loop of that name is
131:    ambiguous. A currently relevant loop-name tick with no provable historical
132:    loop membership is unproven. Tick payload shape, signature, cursor, or
133:    current name validity cannot recover the missing role evidence.
134: 4. For each target runtime name with historical local ticks, require continuous
135:    membership since the relevant tick. A disappearance and later return
136:    conflicts even if its final declaration equals the earlier one. Internal
137:    tracking of membership intervals is evidence analysis, not a newly minted
138:    persistent incarnation ID. Ignore retired names that the target does not
139:    interpret. An ambiguous vertex-name tick matters when the target declares
140:    a vertex boundary; without that consumer the saved period field has no
141:    supported Arrival effect. Later re-enabling that boundary restores the
142:    refusal, not the missing role evidence.
143: 5. Analyze the proposed successor as one additional revision with no fabricated
144:    fact ID, timestamp, ordinal, or Commit. This allows retirement and safe
145:    configuration correction even when the old runtime itself refuses. Run
146:    the check for no-op proposals too; no-op does not certify unsafe execution.

148:    and actual conflicting tick/declaration receipt where available. Do not
149:    manufacture an epoch/cutoff or report guessed identity as proven.

174: ## Generated loop names
175: 
176: Only template sources with a declared `loop` generate runtime loop specs in
177: the current compiler. Bare paths, inline source commands, and templates without
178: such a loop do not create additional loop identities. They must not trigger a
179: blanket source-history refusal.
180: 
181: For a template loop, literal inline parameter rows and the stored loop document
182: can establish generated names without opening the template file. Match the
183: compiler's actual ordering and override semantics: sources sorted by recorded
184: order/subject, parameter rows in order, generated specs overriding explicit
185: specs at equal names. Variables used only by collection commands do not make a
186: literal loop name unprovable.
187: 
188: A `from` parameter file's hash pin commits to historical bytes. If bytes
189: available now verify against the pin recorded for a revision, those bytes can
190: establish that revision's parameter rows. An absent, mismatched, or unpinned
191: file supplies no such evidence. Environment-indirected `kind` remains unknown
192: even in verified rows because the resolved environment value was not recorded.
193: Unknown generators can produce/override any name, including the vertex name.
194: 
195: Keep the classifier pure with explicit `verified_params: hash -> ordered rows`
196: evidence. A shared caller-side collector used by runtime, preparation, and
197: semantic preview obtains candidate bytes from captured historical parameter
198: paths relative to the locator, hashes those exact bytes, and accepts them only
199: for matching recorded pins. Parse the same byte snapshot that was hashed;
200: never verify a path and reopen it to parse potentially changed bytes. Reuse an
201: extracted form of the compiler's parameter-text parser, preserving encoding,
202: header, comments, row ordering, and last-column behavior. Do not implement a
203: second grammar. Cache by verified content hash within this capture only.
204: Unknown/unavailable evidence remains unknown and only blocks a relevant proof;
205: an irrelevant unreadable historical source must not poison a direct loop.
206: No network retrieval or environment resolution supplies historical evidence.
207: 
208: The classifier uses the same whole-value `$NAME` indirection recognition and
209: `$$` leading-dollar escape as the compiler. Partial strings remain literal,
210: matching current behavior. Parameter indirection used only by source commands
211: does not make a literal `kind` unknown. This evidence collector does not replace
212: current runtime pin verification and compilation, which retain their own checks.
213: 
214: Use three-valued membership per name and revision. Direct, implicit, or literal
215: generated membership proves **present** even if another generator has unknown
216: names: an override changes its interpretation but does not remove that name.
217: If the name is not in the provable set and an unresolved generator could emit
218: it, membership is **unknown**. Otherwise it is **absent**.
219: 
220: For every old local loop tick that the target would interpret, membership must
221: be provably present at its receipt and throughout all later revisions through
222: the target. Unknown membership anywhere in that interval refuses: an unknown
223: intervening revision could conceal retirement/recreation without containing a
224: tick itself. Analyze every relevant tick, not just the newest pending edge;
225: hydration also consumes historical reset markers. A tick whose name is absent
226: from the target is not attached to a current loop, so that retired stream alone
227: does not block execution. Unknown target membership for an old tick refuses.
228: 
229: For a vertex-name tick consumed by a target vertex boundary, loop membership
230: at its receipt must be provably absent.
231: Present means a role collision; unknown means its role cannot be established.
232: The vertex identity itself continues while its boundary list is edited or
233: disabled, so only loop-name ambiguity at that tick changes this role proof.
234: Unresolved revisions before all relevant ticks do not, by themselves, create
235: consumption obligations. This is a conservative evidence rule, not proof that
236: unknown expansions actually collided. Literal generated sources and provably
237: continuous direct loops must remain usable. Do not compile old declarations
238: against current external inputs or claim that no document edit proves stability.

The packet's own batch planner appends pending tick drafts into the same `logical` list as facts at `runtime_write.py:1321-1330`, so ticks and facts do share records in the supported path. Whether declaration rows can also share one depends on code not shown, and the design already commits to rejecting unsafe history "imported or appended through other mechanisms."
20: Counterexample: an imported record at ordinal 40 contains `kind-retired x` at seq 0, `tick(name=x, origin=v)` at seq 1, and `kind-defined x` at seq 2. Grouping by ordinal makes `x` continuously present and attaches the tick. Seq-ordering makes the tick fall during absence. The design says both.
21: Fix: state the rule explicitly. Smallest safe rule: any owned tick whose ordinal also carries a same-lineage declaration row is unclassifiable and refuses, naming both coordinates. This is bounded because no supported writer produces that shape.
22: 
23: **B3. Medium: the runtime refusal has no evidence-carrying type.**
24: Engine notes say capture raises `RuntimeWriteRefused` from an issue. That base class at `runtime_write.py:90` carries no basis, captured head, or declaration. `OrdinaryWritePreparationRefused` requires a `fact`, which does not exist at capture time. The SDK notes require "existing normalized refusal family" and "plans report the reason." The declaration side has the same gap: `_preparation_refused` at `arrival_declarations.py:105` has effects and heads but no `cause` slot for the structured issue.
25: Fix: add one `BoundaryContinuityRefused(RuntimeWriteRefused)` with `basis`, `captured_head`, `effective_declaration`, and the issue DTO. Add `cause` to `_preparation_refused`. Both must be raised before signer, collector, or intent creation, which the design already requires.
26: 
27: **B4. Medium: inherit semantics for count boundaries are stated incompletely, and tests will pin whatever falls out.**
28: Engine compat table says "every N to every M: new count starts at zero after last tick." True, but the observable behavior when facts since the edge already exceed M is not stated. `Loop.receive` at `loop.py:111-114` keeps incrementing during hydration and the return value is ignored, so after an edit from `every 10` to `every 5` with 7 facts since the last tick, the count hydrates to 7 and the boundary fires on the next ingress, not retroactively and not after 5 more.
29: The unticked recovery path at `vertex.py:837-846` uses `replayed % count` instead, so a fresh loop and a ticked loop recover differently from identical facts. Under inherit that is acceptable but must be written down, because it is the user-visible meaning of "no silent restart."
30: Related and unstated: the fresh-name route the design recommends instead of restart, at root row 76, hydrates an `after N` loop as already exhausted when at least N older facts route to it, per `vertex.py:840-842`. A user retiring `x` and adding `x2 { after 5 }` gets a boundary that never fires. That is the intended reinterpretation, but the SDK acceptance scenario "first capture states that older facts are being interpreted, not reset" should name this case.
31: Fix: add the three rows to the conformance table and to engine acceptance test 1.
32: 
33: **B5. Low: the params-file rationale is wrong and the negative acceptance text would enshrine an unnecessary refusal.**
34: Root line 154-156 says a `from` file's hash pin "establishes current drift checking, not historical row values." A matching SHA-256 is a commitment to the bytes. When the current file verifies against the pin recorded at revision R, its rows are the rows at R. Engine notes lines 274-276 already say this. Root acceptance text at lines 234-237 then requires refusal for "file-derived generated names ... even when source documents are unchanged," which would lock the over-restriction in.
35: Fix now: narrow the negative scenario to pins that do not verify against current bytes and to env-indirected `kind`. Keep the classifier pure by letting the caller pass `verified_params: Mapping[sha256, rows]` from the read it already performs for pin verification. Prepare and preview may pass an empty map and refuse more than runtime; that is safe. Note env indirection stays unprovable: the resolved value was deliberately not recorded.
36: 
37: ## Missing algorithm detail before implementation
38: 
39: - **Unify the classifier's target input.** Engine notes pass compiled `effective_loop_names`; root passes documents. Use documents in all three call sites so prepare, preview, and capture cannot disagree. Runtime then cross-checks that every compiled current spec name is either provably present or coverable by an unknown generator at the target revision, and refuses otherwise.
40: - **`$$` escape.** The classifier must apply the same whole-value `$NAME` and `$$` rules as `compiler.py:400-426` when deciding whether a literal `kind` is provable.
41: - **Two named tick selections.** Capture, prepare, and preview call `TickRequest(since=float("-inf"))` for the classifier. Hydration and pending planning keep `TickRequest()` at `runtime_write.py:789,1014`. Name them separately in code so a negative-time tick that the classifier refuses is never silently un-replayed by a later widening.
42: - **Cite as built-in.** Membership for `cite` is present from genesis onward regardless of explicit definition or tombstone, per `compiler.py:1008`. A pre-genesis `cite` tick is unproven like any other.
43: - **Prepare no-op path.** Decide whether the noop plan at `arrival_declarations.py:960` runs the classifier on the current state. Recommend yes, so a preview never reports a safe plan that capture refuses one call later.
44: - **Preview C5 gap.** `_arrival_semantic_preview` at `kind.py:123` validates only `proposed_ast.loops`, not literal generated names. Since the C6 classifier computes those, run name reservation over the provable generated set in the same pass.
45: 
46: ## Optional improvements, user decisions, and scoped limitations
47: 
48: **Optional.** Include the last relevant declaration and tick receipt coordinates in every diagnostic so a user can find the retirement without a history dump. Add a positive test that an explicit `cite { after 3 }` retired and re-added inherits the old cite tick as exhausted, since that is the least intuitive consequence of the built-in rule.
49: 
50: **Open user decision.** Inherit versus conservative refusal for in-place trigger/count edits. Recommend inherit. Refusal would block all emission on a store, not one loop, for the most routine edit a user makes, and the inherit semantics are deterministic once B4 is written down. If the user picks refusal, bound it to loops that both have an owned tick and change `boundary.type` or `count`, and leave fold, parse, route, condition, and `when` kind edits inherited.

Pre-genesis owned ticks for a currently interpreted name refuse with rename as the only forward path; state the blast radius in the user-facing note if such stores exist. Negative event-time hydration remains the existing policy. Credential D0/D2 and the explicit transition ceremony are deferred, and nothing here requires a wire reset or incarnation scheme.

===== docs/scratch/arrival-break/consistency-c6-engine-design-notes-2026-09-06.md =====

1: # C6 engine design notes: boundary continuity across declaration history
2: 
3: Status: design for cross-model review. No implementation is authorized by this
4: document. It assumes C3 custody completion and the accepted C5 current-name
5: reservation are already present.
6: 
7: ## Decision to make
8: 
9: D5 says a declaration edit changes interpretation without rewriting facts, while
10: an unchanged boundary identity keeps its established consumption edge. Restart
11: and reincarnation must be explicit; a declaration hash is not a boundary ID
12: ([identity decisions D5](identity-decisions-2026-09-06.md#d5--declaration-edits-preserve-history-reset-must-be-explicit)).
13: C6 exists because the current runtime cannot distinguish a continuously defined
14: loop from a retired and later recreated loop that happens to reuse its name
15: ([consistency matrix C6](consistency-contract-matrix-2026-09-06.md#prioritized-worklist)).
16: 
17: The bounded policy proposed here is **inherit by runtime role and name while the
18: role remains continuously present**:
19: 
20: - A loop is `(vertex name, loop role, loop name)`. In-place edits retain that
21:   identity and its last recorded edge. This includes changing `when`/`after`/
22:   `every`, counts, matches, conditions, folds, parse, routes, run commands and
23:   read facets. Those changes can alter current and future conclusions; that is
24:   the append-forward reinterpretation D5 already permits.
25: - Retiring the whole loop ends its presence epoch. Recreating the same name may
26:   reuse an earlier epoch's local tick under the current implementation. Refuse
27:   the recreation when such a tick exists. A tick-free retirement/recreation is
28:   permitted: facts alone are interpretation input and make no persisted claim
29:   that a boundary was consumed.
30: - A vertex boundary is `(vertex name, vertex-boundary role)`. Its several trigger
31:   clauses all produce the same tick name and share one vertex-period edge.
32:   Editing the clause tuple, including empty then nonempty, retains the role; it
33:   is not treated as a new incarnation.
34: - A historical local tick whose role was ambiguous when received is not repaired
35:   by a later C5 configuration correction. In particular, if `origin == name ==
36:   vertex` and a same-named loop existed at that receipt coordinate, a current
37:   vertex boundary cannot safely consume it as a vertex-period edge. A repair
38:   with no such tick is valid. Removing the vertex-boundary consumer as well as
39:   the colliding loop leaves the ambiguous row available for inspection but out
40:   of runtime state.
41: 
42: This is intentionally narrower than semantic equivalence. It does not try to
43: prove that two folds or predicates compute the same result.
44: 
45: The vertex-role refusal is consumer-scoped. `hydrate_snapshot` assigns
46: `_vertex_period_start` for a local vertex-name tick, but supported detached
47: execution reads that value only while a current vertex boundary exists:
48: ordinary ingress gates its initialization on `_has_vertex_boundary`
49: ([vertex.py:662](../../../libs/engine/src/engine/vertex.py#L662)), and pending
50: planning has the same gate ([vertex.py:1319](../../../libs/engine/src/engine/vertex.py#L1319)).
51: `_evaluate_vertex_only_boundaries` is reached only behind the current
52: `_has_vertex_boundary` check ([vertex.py:1204](../../../libs/engine/src/engine/vertex.py#L1204));
53: the surrounding legacy evaluator also requires an attached store, while the
54: Arrival candidate is storeless. C5 prevents a current same-named loop from
55: reading the row through the loop path. Therefore an ambiguous historical tick
56: does not block a target with neither consumer. A proposal that adds a vertex
57: boundary must re-run the check and refuse.
58: 
59: ## What the engine actually does
60: 
61: ### Recorded ticks are edges, not state checkpoints
62: 
63: `Vertex.hydrate_snapshot` merges facts and ticks by receipt coordinate. For an
64: owned tick (`tick.origin == vertex.name`), it looks up the **current** loop by
65: `tick.name`, calls `Loop.replay_boundary`, and independently treats
66: `tick.name == vertex.name` as a vertex-period edge
67: ([vertex.py:769](../../../libs/engine/src/engine/vertex.py#L769),
68: [vertex.py:784](../../../libs/engine/src/engine/vertex.py#L784)). It never reads
69: the old tick payload, `since`, fact cursor, window hash or signature into fold
70: state.
71: 
72: `Loop.replay_boundary` applies the **current** loop's reset/count mode: reset
73: returns the current projection to its current initial value, `every` zeros the
74: count, and `after` marks it exhausted
75: ([loop.py:157](../../../libs/engine/src/engine/loop.py#L157)). Therefore an old
76: edge under a current `after` definition means “already exhausted”; under a
77: current `every` definition it is the edge from which the new count resumes.
78: That result should be explicit in tests, rather than described as preservation
79: of the old trigger policy.
80: 
81: Facts are always routed, parsed and folded under the current candidate
82: ([vertex.py:821](../../../libs/engine/src/engine/vertex.py#L821)). This is why a
83: fold-only edit is not an “incompatible tick payload” in today's engine: no tick
84: payload is deserialized. Historical tick payloads remain raw evidence. If a
85: future runtime hydrates from payload checkpoints, it will need a persisted
86: checkpoint schema/compatibility claim and is outside this slice.
87: 
88: ### Pending boundaries use the same name edge on a different ordering axis
89: 
90: Source-mode pending evaluation builds the latest owned edge per tick name using
91: event time with receipt coordinate as its tie-break, then scans eligible facts
92: by event time and receipt coordinate
93: ([vertex.py:1260](../../../libs/engine/src/engine/vertex.py#L1260)). This is
94: correctly distinct from the declaration-history question: which definition was
95: in force at a tick is determined by the tick's **receipt coordinate**, not its
96: event timestamp. The validator must not replace either ordering with the other.
97: 
98: Count boundaries are not invented by pending evaluation
99: ([vertex.py:1275](../../../libs/engine/src/engine/vertex.py#L1275)); their restored
100: counter/exhaustion state comes from hydration
101: ([vertex.py:835](../../../libs/engine/src/engine/vertex.py#L835)). A continuity
102: guard must therefore run before both ordinary planning and source pending
103: planning.
104: 
105: ### The supported declaration surface currently has reset only
106: 
107: The generic engine permits `reset=False`, but historized `LoopDef` has no reset
108: field ([ast.py:518](../../../libs/lang/src/lang/ast.py#L518)). Every DSL boundary
109: maps to `reset=True`, and materialization copies that value into `Loop`
110: ([compiler.py:541](../../../libs/engine/src/engine/compiler.py#L541),
111: [compiler.py:981](../../../libs/engine/src/engine/compiler.py#L981)). The
112: programmatic carry form is therefore not a supported Arrival declaration
113: transition today.
114: 
115: No reset/carry field should be invented in C6. If one is added later, changing
116: it in the presence of an earlier local tick must require the explicit transition
117: ceremony: otherwise `replay_boundary` retroactively applies the new choice to
118: every old edge. Low-level callers that construct a detached `Vertex` remain
119: caller-responsible; the supported Arrival authority path reconstructs from
120: historized documents.
121: 
122: ### Final effective documents are insufficient
123: 
124: The snapshot declaration resolver seeds the genesis document set, applies own-
125: lineage definitions/tombstones in receipt order, and returns only the surviving
126: documents ([declaration.py:221](../../../libs/engine/src/engine/declaration.py#L221)).
127: That correctly answers “what is effective now,” but erases the retirement that
128: distinguishes continuous presence from reincarnation.
129: 
130: Runtime construction fetches all internal facts, resolves only the final set,
131: compiles/materializes a new candidate, then hydrates it with ticks
132: ([runtime_write.py:715](../../../libs/engine/src/engine/runtime_write.py#L715)).
133: Declaration preparation currently requests declaration facts only, resolves the
134: final set, diffs the proposal and starts signing
135: ([arrival_declarations.py:799](../../../libs/engine/src/engine/arrival_declarations.py#L799)).
136: Both call sites need the same historical analysis before hydration or signing.
137: 
138: ## Proposed bounded implementation
139: 
140: ### 1. Pure receipt-history analyzer
141: 
142: Add a small engine module, tentatively `arrival_boundary_continuity.py`, with no
143: store or registry access:
144: 
145: ```python
146: @dataclass(frozen=True)
147: class BoundaryContinuityIssue:
148:     reason: Literal[
149:         "prior-incarnation",
150:         "ambiguous-tick-role",
151:         "unproven-generated-incarnation",
152:         "invalid-projection-shape",
153:     ]
154:     vertex_name: str
155:     loop_name: str | None
156:     tick_id: str
157:     tick_ordinal: int
158:     tick_seq: int
159:     declaration_fact_id: str | None
160:     epoch_started_at: tuple[int, int] | None
161:     retired_at: tuple[int, int] | None
162: 
163: def analyze_boundary_continuity(
164:     anchor: DeclarationAnchor,
165:     facts: Sequence[Fact],
166:     ticks: Sequence[Tick],
167:     *,
168:     target_documents: Sequence[Mapping[str, object]],
169:     verified_params: Mapping[str, tuple[Mapping[str, str], ...]] | None = None,
170:     compiled_loop_names: Collection[str] | None = None,
171: ) -> BoundaryContinuityIssue | None: ...
172: ```
173: 
174: The target is documents at every call site. Runtime may also supply the compiled
175: current name set as a cross-check: every compiled name must
176: be provably present, be the implicit `cite`, or be coverable by an unknown
177: generator at the target revision. A mismatch refuses rather than letting
178: prepare, preview and capture silently use different namespace algorithms.
179: 
180: The exact DTO names are not protocol. The analyzer returns structured evidence
181: and does not choose an SDK error. Runtime capture needs one new
182: `BoundaryContinuityRefused(RuntimeWriteRefused)` carrying `basis`,
183: `captured_head`, `effective_declaration`, and the issue. It should expose the
184: issue's stable `tick_id`, `ordinal`, loop/vertex name, and declaration coordinate
185: as scalar diagnostic fields, plus `coordinator_phase="prepare"` and explicit
186: custody-not-entered effects. This is the planning attempt's mutation proof; an
187: earlier registry open may still have advanced witness evidence.
188: 
189: Declaration preparation keeps its existing `DeclarationPreparationRefused`.
190: It can raise that wrapper explicitly `from` a continuity-conflict exception,
191: with captured H and its existing C2 prepare/custody-not-entered fields. The SDK
192: normalizer already follows `__cause__`; there is no demonstrated need to add a
193: general `cause` parameter to `_preparation_refused`. Raw evidence readers,
194: inspection, verification and export do not call the analyzer.
195: 
196: The analyzer:
197: 
198: 1. Validates/uses the already licensed declaration anchor. It seeds state from
199:    the own genesis `documents` and ignores foreign/absent-lineage declaration
200:    rows exactly as the resolver does.
201: 2. Sorts declaration facts and ticks by `(arrival_ordinal, arrival_seq)`. It
202:    applies every declaration fact sharing one `arrival_ordinal` as one atomic
203:    revision before moving to the next record. A wire `batch` contains fact rows
204:    only, so there is no legitimate tick halfway through a declaration ceremony
205:    ([arrival_body.py:179](../../../libs/engine/src/engine/arrival_body.py#L179)).
206:    `FileLedger.append` may commit several drafts in one CAS, but
207:    `append_marked_many` assigns each draft its own next outer ordinal
208:    ([arrival_file_backend.py:321](../../../libs/engine/src/engine/arrival_file_backend.py#L321),
209:    [arrival.py:1517](../../../libs/engine/src/engine/arrival.py#L1517)). A query
210:    returning a tick at an ordinal that also contains fact rows contradicts both
211:    legal wire expansions. Refuse it as `invalid-projection-shape`, naming the
212:    conflicting coordinates; do not invent a transient mid-record definition
213:    state. This is defensive adapter validation, not a supported boundary event.
214: 3. Tracks uninterrupted presence epochs for **all materialized loop names**, not
215:    merely loops that currently declare a boundary. Membership at each atomic
216:    revision is three-valued: present, absent, or unprovable from recorded
217:    template inputs. Hydration calls `replay_boundary` on a matching passive loop
218:    too.
219: 4. Classifies only owned ticks. Foreign and originless ticks remain visible but
220:    establish no local edge, matching `_owns_tick`.
221: 5. For every current loop name, requires every owned matching tick to have a
222:    continuously **present** membership from that tick's receipt through the
223:    target revision. A tick before genesis, during absence, or in an earlier
224:    retired epoch makes the current consumption unproven. So does an unresolved
225:    intermediate revision after an otherwise known tick: it may conceal an
226:    absence/recreation, and the later known definition cannot repair that gap. An
227:    unresolved revision entirely before the latest relevant tick does not matter
228:    if membership is provably present from that tick forward. A current loop with
229:    no such tick is clean and is allowed, even if facts of that kind predate it.
230: 6. If the current runtime has a vertex boundary, checks each owned tick named
231:    for the vertex against the definition state at that tick's receipt. A
232:    same-named loop in force there is an ambiguous role; pre-genesis role is
233:    likewise unproven. If there is no current vertex-boundary consumer, the row
234:    does not block runtime execution, but a proposal that adds one is checked and
235:    refused.
236: 7. Applies the compiler's whole-value parameter rules when deriving literal
237:    generated names: `$NAME` is environment-indirected and unknown, `$$value`
238:    is the literal `$value`, and other values are literal
239:    ([compiler.py:400](../../../libs/engine/src/engine/compiler.py#L400)). It also
240:    runs the C5 name reservation over every provable generated name, so semantic
241:    preview and declaration preparation do not omit literal template collisions.
242: 
243: The query must request the full bounded tick prefix, not the convenience time
244: default. `TickRequest()` starts at `0.0`
245: ([arrival_contract.py:248](../../../libs/engine/src/engine/arrival_contract.py#L248)),
246: while wire timestamps are finite but need not be nonnegative. Use
247: `TickRequest(since=float("-inf"))`, keep the snapshot's captured-head bound, and
248: sort by receipt coordinate inside the analyzer. This establishes continuity
249: from the whole receipt prefix. Existing hydration/pending timestamp selection
250: must not be widened as an incidental C6 change; if the runtime keeps its current
251: nonnegative convenience request, name the two tick selections separately and
252: test the negative-time history guard explicitly.
253: 
254: ### 2. Runtime integration before materialization effects
255: 
256: In `_build_effective_arrival_candidate`:
257: 
258: 1. Fetch facts and the complete continuity tick prefix from the same CURRENT
259:    snapshot. Keep any narrower runtime tick selection explicit rather than
260:    silently relying on `TickRequest()` in both roles.
261: 2. Resolve and compile the current declaration, including final template specs.
262: 3. Analyze continuity before `materialize_vertex` and before
263:    `hydrate_snapshot`.
264: 4. Store the already checked facts/ticks in `RuntimeCapture`; ordinary and batch
265:    preparation already compose `capture_runtime`, and source preparation calls
266:    `capture_runtime(source_mode=True)` before collector construction
267:    ([arrival_sources.py:477](../../../libs/engine/src/engine/arrival_sources.py#L477)).
268: 
269: This single chokepoint covers supported ordinary, batch, pending-boundary and
270: source paths. `plan_batch_from_capture` needs no second historical scan because
271: the immutable capture was validated at its exact basis. Later source tiers
272: recapture and already refuse changed declaration documents before collection
273: ([arrival_sources.py:959](../../../libs/engine/src/engine/arrival_sources.py#L959));
274: the new capture performs continuity validation as well.
275: 
276: The guard must run before fold initializers or external collectors. Template
277: compilation already performs pinned source reads in runtime construction, so
278: the bounded slice does not add a second live locator/declaration read.
279: 
280: ### 3. Declaration proposal integration before signing
281: 
282: `prepare_declaration_edit` should fetch all declaration facts and the complete
283: tick prefix from its existing snapshot. After `diff_documents`, simulate the
284: proposal as one next atomic revision and analyze the resulting current runtime
285: roles before building `_declaration_row` or invoking any signer. This preserves
286: C5's append-forward correction rule:
287: 
288: - removing a currently invalid collision is permitted when no recorded tick
289:   makes the remaining vertex role ambiguous;
290: - a collision that did produce an ambiguous tick cannot be “proved repaired” by
291:   merely adding a unique loop;
292: - retirement is permitted; recreation is refused only when the new current loop
293:   would consume an owned tick outside its new epoch;
294: - a never-used name and a tick-free retired name are permitted.
295: 
296: The no-op path should analyze the current state too if it is returned as an
297: executable declaration basis; otherwise a no-op could report a safe plan that
298: runtime capture immediately refuses. The result remains a refusal before intent,
299: cache publication, signing or append. Initialization needs no C6 history check:
300: there is no earlier local tick; C5 proposed-name validation remains its guard.
301: 
302: ### 4. Template-generated names
303: 
304: The runtime final map is direct specs updated by template specs
305: ([runtime_write.py:760](../../../libs/engine/src/engine/runtime_write.py#L760)).
306: Template source documents retain their loop definition, inline parameter forms,
307: and hashes for template/parameter files, but not resolved environment values or
308: old file bytes
309: ([document.py:603](../../../libs/lang/src/lang/document.py#L603)). Compilation
310: loads parameter files and resolves whole-value `$ENV` indirection at runtime
311: ([compiler.py:429](../../../libs/engine/src/engine/compiler.py#L429)).
312: 
313: Consequently the analyzer must not claim it can reconstruct every historical
314: expanded name:
315: 
316: - Literal inline `with kind=...` rows are reconstructible from each recorded
317:   source-document revision. Treat their generated names like direct loops.
318: - An unchanged external parameter-file recipe can be reconstructed only while
319:   the current file verifies against the same recorded hash; an older replaced
320:   hash without retained bytes cannot be reconstructed.
321: - An environment-indirected kind is never historical identity evidence because
322:   its resolved value was deliberately not absorbed. Its generated membership is
323:   unprovable for the entire declaration revision, even if the current expansion
324:   happens to name a known loop.
325: - Source entries with no loop spec do not add loop names and are irrelevant to
326:   this check. Command/cadence-only edits do not create an incarnation.
327: - A direct or implicit loop that is provably present keeps membership present
328:   even while another template's generated-name set is unknown. A generated
329:   override can change the spec, but inherit-by-role/name treats that as an
330:   in-place interpretation edit; the unknown source cannot conceal absence of a
331:   name another recorded definition guarantees.
332: 
333: The bounded safe fallback is refusal only when the current runtime would consume
334: an owned tick whose continuous generated-loop epoch cannot be proven. An
335: unresolved revision at the tick or anywhere after it is such a gap, even if the
336: current revision is known again; otherwise remove/recreate could hide inside the
337: unknown interval. Do not refuse a dynamic template merely because it exists,
338: and do not use today's env or unpinned bytes as yesterday's proof. If compiler
339: work cannot retain enough per-spec provenance without widening the slice,
340: reject the unprovable tick case and leave richer template continuity for a
341: follow-up.
342: 
343: Keep the analyzer pure by passing already verified parameter rows keyed by their
344: recorded SHA-256. Runtime construction may populate that map from the same reads
345: it already performs for source-pin verification. A matching hash commits to the
346: file bytes at that declaration revision, so the classifier may use those rows;
347: the pin is more than a generic “current drift” flag. Declaration preparation and
348: semantic preview may pass no verified historical rows and conservatively leave
349: those generated memberships unknown. A missing/mismatched pin and an
350: environment-indirected `kind` remain unknown. Current external bytes are never
351: used for an older different hash.
352: 
353: The implicit `cite` loop is also materialized even when undeclared
354: ([compiler.py:1003](../../../libs/engine/src/engine/compiler.py#L1003)). Treat it
355: as a continuously present built-in role for the supported runtime epoch; an
356: explicit `cite` definition changes its interpretation in place rather than
357: retiring its name. A local `cite` tick before the historized epoch remains
358: unproven.
359: 
360: ## Compatibility table
361: 
362: | Transition with current consumer | Local tick evidence | Proposed result |
363: | --- | --- | --- |
364: | Fold/search/preview/edge/lifecycle/run edit | any tick in current presence epoch | allow; current interpretation, same edge |
365: | `when` trigger/match/condition edit | any tick in current presence epoch | allow; pending facts after the edge use new predicate |
366: | `every N` to `every M` | prior loop tick | allow; new count starts at zero after last tick |
367: | `every` to `after` | prior loop tick | allow; current `after` is already exhausted |
368: | `after` to `every` | prior loop tick | allow; current `every` resumes from last tick |
369: | Remove boundary but retain loop | prior loop tick | allow; historical reset edge still partitions current replay |
370: | Remove loop and leave it absent | prior loop tick | allow; no current loop consumes the row |
371: | Remove then recreate loop | no owned tick before new epoch | allow; facts are reinterpreted, no persisted edge is reused |
372: | Remove then recreate loop | owned tick before new epoch | refuse; incarnation is not recorded |
373: | Add never-declared loop | no prior owned same-name tick | allow |
374: | Add apparently new loop | prior/pre-genesis owned same-name tick | refuse; clean identity is unproven |
375: | Repair C5 loop/vertex collision | no ambiguous tick | allow |
376: | Repair collision but retain vertex boundary | ambiguous local vertex-name tick | refuse while vertex boundary would consume it |
377: | Same-name foreign/originless tick | any transition | ignore for continuity; it is not a local edge |
378: | Change reset/carry | earlier local tick | not expressible now; future explicit transition required |
379: 
380: The count rows above need these exact observable qualifications:
381: 
382: - With a prior loop tick, hydration resets current `every` bookkeeping at the
383:   tick and then increments for every later routed fact. It suppresses firing
384:   during hydration and does not reduce the accumulated count modulo the new
385:   threshold. If seven facts follow the edge under current `every=5`, the **next
386:   ingress fires** (count becomes eight); no retroactive tick is minted and it
387:   does not wait five more facts.
388: - With no prior loop tick, hydration uses `events_folded % count` for `every`.
389:   Seven folded facts under `every=5` leave two counted, so the next boundary is
390:   after three more routed ingresses. The ticked and unticked cases deliberately
391:   differ because a recorded tick is an exact reset edge.
392: - With a prior loop tick, current `after=N` is exhausted by `replay_boundary`
393:   regardless of facts later in the prefix. With no prior tick, `after=N` is
394:   marked exhausted when replayed facts are already at least `N`; below `N`, the
395:   next ingresses continue from the replayed count. Thus replacing retired `x`
396:   with clean `x2 { after=5 }` can immediately be exhausted by five older facts.
397:   That is current reinterpretation, not an implicit fresh-facts cutoff.
398: 
399: ## Acceptance tests for an implementation slice
400: 
401: Use real signed declaration history and a real file projection for the public
402: preparation/capture tests; pure analyzer tests can use small DTO fixtures.
403: 
404: 1. A continuously present `every=2` loop fires, is edited to `every=3`, and
405:    resumes counting from the recorded tick. Cover both fewer-than-threshold and
406:    at/above-threshold post-tick fact counts; at/above fires on the next ingress,
407:    never during hydration. Contrast the unticked modulo case. `every -> after`
408:    with a tick stays exhausted, `after -> every` resumes, and an unticked
409:    `after=N` is exhausted when replay already has at least N facts. Also prove a
410:    clean replacement name with `after=N` interprets older facts rather than
411:    receiving a fabricated fresh cutoff. These pin inherit-by-name rather than
412:    accidental old-policy replay.
413: 2. Fold-only, condition, route, parse, presentation and run edits with a prior
414:    tick are accepted and deterministically use current interpretation.
415: 3. A boundary is removed while its loop stays passive; hydration still applies
416:    the existing edge. Re-adding the boundary stays the same loop epoch.
417: 4. Whole-loop remove/recreate with an earlier owned tick refuses declaration
418:    preparation before signing and append. The same history without a tick is
419:    accepted even with old facts. Removal without recreation remains executable.
420: 5. An already-recorded/imported unsafe recreation refuses ordinary capture,
421:    batch and source preparation before signing, append, pending tick planning or
422:    collector construction. Handles close through existing capture cleanup.
423: 6. A C5 collision followed by a local ambiguous tick and then a configuration
424:    repair still refuses a current vertex-boundary consumer. The tick-free repair
425:    succeeds. Removing the vertex-boundary consumer leaves evidence reads usable.
426: 7. Passive current loops are included: an out-of-epoch tick refuses even though
427:    the loop declares no boundary. Foreign and originless same-name ticks do not.
428: 8. Multiple declaration changes in one Arrival ordinal are one state transition;
429:    source replacement does not create a false intermediate incarnation. An
430:    injected query that places a tick beside facts at the same ordinal refuses as
431:    invalid projection shape; supported FileLedger append proves its records have
432:    distinct ordinals.
433: 9. A negative-event-time tick is detected through the full receipt-prefix
434:    request.
435: 10. Static literal generated names get the same epoch behavior, including `$$`
436:     literal escaping and C5 vertex-name reservation. A params file whose current
437:     bytes verify the recorded revision hash is usable evidence. Env-indirected,
438:     missing-pin, mismatched-pin, or older replaced-hash generated membership is
439:     unknown and refuses only when a current consumer would reuse an owned tick;
440:     a source with no loop is unaffected.
441: 11. Raw read, inspection, verification and exact export still expose histories
442:     that runtime execution refuses.
443: 
444: ## Explicit transition deferred
445: 
446: Refusal is not a restart mechanism. A later append-forward transition needs a
447: reviewed declaration event that says which `(vertex, role, name)` is being
448: continued or restarted and establishes the receipt cutoff for the new
449: incarnation. Hydration and pending evaluation would then select edges within
450: that declared incarnation. The event must also define reset/carry behavior and
451: how an operator adjudicates old C5 role ambiguity. It must not rewrite existing
452: facts/ticks or infer intent from a declaration hash.
453: 
454: That future ceremony may avoid changing the tick wire shape by making the
455: incarnation interval a declaration-history claim, but its vocabulary,
456: authorization, import behavior and recovery semantics require protocol review.
457: C6's first slice should only refuse cases that current evidence cannot classify.
458: 
459: ## Limits to state plainly
460: 
461: - This is a role/name continuity check, not a full projection-vs-ledger audit or
462:   authorship verification pass.
463: - It does not prove semantic equivalence of folds, routes, parse steps or
464:   predicates. D5 permits those to reinterpret facts under the retained edge.
465: - Current declaration history cannot prove old environment values or replaced
466:   external parameter-file contents. The design refuses affected edge reuse
467:   rather than substituting current ingress.
468: - Facts without a tick do not prove a consumed boundary. Allowing their current
469:   reinterpretation may cause a newly declared pending boundary to fire; that is
470:   the requested current interpretation, not a recovered historical claim.
471: - Histories predating declaration genesis have no definition timeline. A current
472:   role must not consume a pre-genesis local tick unless a later explicit
473:   transition classifies it.
474: - Generic/legacy `Vertex` construction and evidence-only reads retain their
475:   current behavior. The guard belongs to supported Arrival authority planning
476:   and declaration preparation.


===== docs/scratch/arrival-break/consistency-c6-sdk-design-notes-2026-09-06.md =====

1: # C6 SDK boundary continuity design notes
2: 
3: ## Finding
4: 
5: The supported Arrival writer captures effective declaration documents, facts,
6: and ticks at one CURRENT basis, then hydrates a detached runtime
7: ([runtime_write.py](../../../libs/engine/src/engine/runtime_write.py#L719-L850)).
8: Hydration treats every tick with `origin == effective vertex name` as local and
9: applies a matching tick name to the current loop, even when that loop is
10: passive ([vertex.py](../../../libs/engine/src/engine/vertex.py#L769-L819)). An
11: in-place declaration edit therefore reuses its old tick's reset/count/period
12: effect by policy. A vertex tick has the
13: same name as the vertex, so a historical C5 collision (`origin == name` and
14: `tick.name == name`) cannot be classified after a later declaration correction.
15: It matters to supported runtime continuity only when the corrected target has a
16: vertex-boundary consumer; without one, the row remains evidence but has no
17: current loop or vertex-boundary effect.
18: 
19: This is not a reason to restrict ordinary interpretation. Facts are deliberately
20: re-folded under the bounded effective declaration; hydration does not restore
21: old tick payloads as fold state. Existing `diff_documents` already rejects a
22: vertex rename as a normal declaration edit
23: ([document.py](../../../libs/lang/src/lang/document.py#L1100-L1157)). C5
24: separately rejects a *current* loop/vertex name collision. C6 is about historical
25: tick consumption, not credentials, observer equivalence, key locations, or
26: lineage identity (D0/D2 remain separate).
27: 
28: ## Proposed public policy
29: 
30: Use the effective declaration and complete bounded tick stream at the
31: declaration/runtime capture head. Only ticks owned by the effective vertex
32: (`origin` exactly equals its declared name) participate; foreign or originless
33: ticks remain evidence and never block a transition. Compare names exactly.
34: 
35: The supported identity is the exact `(vertex name, boundary role, boundary
36: name)` and its continuous membership interval, rather than a declaration or
37: boundary fingerprint. An in-place trigger/count, condition, fold, parse, route,
38: or dispatch edit inherits that identity's recorded edge. The current compiler
39: fixes `reset=True` for all DSL boundary forms
40: ([compiler.py](../../../libs/engine/src/engine/compiler.py#L541-L593)); if reset
41: or carry becomes declarative later, changing it is an explicit-transition
42: question, not an inferred identity change. Source, search, presentation,
43: lifecycle, and observer edits remain ordinary interpretation changes.
44: 
45: Generated source loops need a stricter evidence rule. Only a template source
46: with a declared `loop` can generate additional runtime loop identities; bare
47: paths, inline collection commands, and templates without `loop` do not. Literal
48: inline parameter rows plus the absorbed loop document can establish generated
49: names. A `from` parameter file can establish historical rows **only** when the
50: currently read bytes verify against that revision's recorded SHA-256 pin. The
51: pin then commits to those bytes and its parsed rows. Environment-indirected
52: values remain unprovable because their resolved value was not recorded.
53: 
54: The classifier records membership as **present**, **absent**, or **unknown** at
55: each revision. Direct declaration loops and implicit `cite` are present despite
56: an unresolved generator; unknown generated membership never overrides that
57: proof. Verified file-pin rows establish the corresponding generated names in
58: their recorded order. Unknown means only that a dynamic generator could add or
59: override an otherwise unproven name; it is never treated as absent.
60: 
61: Use one shared evidence loader for runtime capture, declaration preparation,
62: and semantic preview. Given the bounded declaration revision's pin and source
63: location, it reads bytes, hashes before trusting them, and, only on a match,
64: parses them with the compiler's actual parameter parser. Its output is a pure
65: `verified_params` mapping from recorded hash to ordered parameter rows; it does
66: not resolve environment values. Extract a text-to-rows parser from the compiler
67: if necessary rather than creating a second grammar. A missing, unreadable,
68: mismatched, or malformed file contributes no historical rows. If an owned local
69: tick occurs during such an unresolved generated revision, continuity is
70: **unprovable** for the affected runtime capture or plan even when today's source
71: document is unchanged. Do not load current environment/files as history. A
72: command-only source edit is ordinary when full history proves its generated
73: name literal and stable; it does not itself reset a boundary.
74:

84: 
85: Retiring an old loop and adding a fresh, unique loop name creates a distinct
86: future tick identity. It is **not** a restart: it neither cuts off old facts nor
87: promises that a new interpretation will not fold or fire on them. It does not
88: carry state or translate old facts/ticks. A current C5 collision with no tick
89: can use that configuration repair. A collision that already produced a tick
90: cannot be made executable with a current or re-added vertex boundary merely by
91: renaming a later loop, because that row is also shaped like a vertex period
92: tick. Without a vertex-boundary consumer, the corrected target may run and
93: retains the ambiguous row as evidence.
94: 
95: ## Explicit transition, deferred implementation
96: 
97: The alternative is a new signed declaration-ceremony transition, for example
98: `plan_boundary_transition`/`apply_boundary_transition`, rather than an option
99: silently attached to `edit_kind`. It would atomically append the successor
100: declaration documents and a durable transition fact at one exact H. Its body
101: must name the scope (loop or vertex), old/new names, action (`restart` or
102: retire), predecessor evidence, and its effective receipt coordinate. Runtime
103: capture would reconstruct declaration transitions
104: from the bounded declaration stream and ignore pre-cutover tick consumption for
105: the transitioned scope. The result exposes captured H, transition fact ID,
106: Commit/outcome, and post-commit projection status just as declaration edits do.
107: 
108: That does not change the tick wire format, but it is new declaration vocabulary
109: and replay behavior. It needs a separate compatibility decision for historical
110: reads and for vertex-boundary restarts; it must never relabel old ticks. Until
111: then, do not expose a `reset`, `carry`, same-name recreation, or alias parameter
112: on the existing SDK edit APIs.
113: 
114: ## Entry-point worklist
115: 
116: 1. Extract a pure continuity classifier over `(full bounded declaration
117:    history through H, proposed-after, bounded owned ticks,
118:    verified_params)`. It must reconstruct exact role/name membership
119:    intervals across retired/recreated/imported history, not compare only
120:    effective-before/effective-after documents. Use it in
121:    `prepare_declaration_edit` and `_arrival_semantic_preview`; plans report the
122:    reason before draft/signature use. Run it for a no-op target as well: a
123:    no-op must not claim safe applicability when runtime capture would refuse.
124:    Initialization has no pre-genesis history, so C5's existing new-declaration
125:    validation is sufficient there.
126: 2. Run the same classifier in `capture_runtime`, ordinary/batch preparation,
127:    and source invocation preparation. A local cache cannot bypass a historized
128:    unsafe transition. Its tick input must explicitly request
129:    `TickRequest(since=-inf, until=inf)`: the contract default is `since=0`,
130:    which is not a complete historical range. Preserve C5's current-name
131:    validator as a separate check.
132: 3. Keep `preview_emission`, `emit_fact`, `emit_batch`, and `run_sources` on the
133:    existing normalized pre-append refusal path. Credential providers may load
134:    existing signer callables before capture, but those callbacks are not called;
135:    no signing,
136:    collector, append, or maintenance action begins after a continuity refusal.
137: 4. Leave `read_facts`, summary, state, timeline, inspection, verify, and export
138:    usable for unsafe histories. They return their normal bounded basis/evidence;
139:    none claims runtime execution is safe.
140: 
141: `capture_runtime` already opens `ProjectionRequirement.CURRENT`; so do ordinary,
142: batch, preview, and source paths that delegate to it. SDK
143: `_arrival_semantic_preview` also uses `_open_arrival_read(... CURRENT)` and
144: must pass that snapshot's complete `_decl` facts plus full-range ticks to the
145: pure classifier. `prepare_declaration_edit` likewise has a CURRENT snapshot
146: and all declaration facts but must add the explicit full-range tick request.
147: Both it and semantic preview obtain `verified_params` from the common loader.
148: The classifier's provable target runtime-name set, including literal generated
149: names, must also feed C5's namespace validator; checking only
150: `proposed_ast.loops` leaves a generated-name collision preview gap. No C6
151: decision needs `ALLOW_BEHIND`, a legacy reader, or a second snapshot.
152: 
153: ## Acceptance scenarios
154: 
155: - A loop with an owned tick accepts fold-only and count/when/match edits, then
156:   emit/preview resumes with the preserved boundary edge. It does not refire a
157:   previously consumed observation under the new rule.
158: - Removing a ticked loop succeeds; adding the same name later refuses. A
159:   fresh-name successor has a distinct future tick identity, without claiming a
160:   fact cutoff, reset, or state carry.
161: - A new boundary on a tick-free loop is accepted and its first capture states
162:   that older facts are being interpreted, not reset.
163: - A legacy C5 collision without ticks is corrected by an append-forward edit
164:   and can run. With an owned ambiguous tick, a target that declares a vertex
165:   boundary refuses; without that consumer, runtime/source/emit may run while
166:   fact/tick reads, inspection, verify, and export retain the row as evidence.
167: - Proposed and local declarations disagree: the effective captured documents
168:   and owned ticks decide the refusal; no cache edit or concurrent declaration
169:   advance can widen the plan. A full-head CAS still protects execution.
170: - A command-only source edit with a fixed literal kind keeps an owned boundary
171:   edge only when full declaration history proves the generated identity. A
172:   pinned parameter file with bytes matching its recorded hash supplies those
173:   historical rows; a mismatched/missing file and environment-indirected kind
174:   refuse with owned ticks even if source text is unchanged.
175: 
176: The unresolved product decision is whether the explicit transition ceremony is
177: worth supporting before a future tick boundary-ID wire revision. The conservative
178: matrix above is implementable without that decision and does not narrow the
179: user's ability to reinterpret facts or inspect historical evidence.
