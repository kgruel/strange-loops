Specification 02 · portable interchange

Arrival Wire Format

A deterministic UTF-8 JSON Lines representation of Arrival records. It is the reference interchange codec and file-backend format, not a mandatory second store.

Wire v1 Branch-compatible envelope 26 August 2026
01

Role and compatibility

Wire v1 starts from the envelope implemented by libs/engine/src/engine/arrival.py on this branch, but does not freeze it: decision:design/arrival-wire-v1-seam-triage (26 August 2026) pins wire v1 as the post-triage envelope — drop body.t, re-spell the tick observer, keep the dual signature. No shipped store exists in the branch format, so the triage costs codec and fixture regeneration only; the branch’s behavioral convergence does not reopen.

Ruling

A backend is conforming when it can validate and reproduce the logical records in this format. Its tables and pages do not need to contain these exact line bytes. A .arrival artifact is authoritative only when the explicit store descriptor selects the file backend.

02

Framing and transport bytes

  • The decoded stream MUST be UTF-8.
  • Each record MUST be one JSON object followed by a single LF byte (0x0a).
  • A canonical emitter MUST use compact separators and JSON escapes so no raw newline occurs inside a record.
  • A decoder MUST reject duplicate object keys at every grammar level it interprets.
  • A finalized export MUST end with LF. An unterminated final record is a truncated export.
  • Blank lines, comments, byte-order marks, and non-record headers are not permitted.

Live file exception

A lock-free reader following a live file backend MAY temporarily ignore one unterminated tail because it cannot distinguish an interrupted write from an append in flight. Only a writer holding the backend’s append lock may truncate that tail. This exception does not apply to a finalized import or archive.

Compression

A transport or archive MAY compress the stream. Compression is outside the record format: after decompression, the same newline-framed bytes and manifest claims must emerge. Filenames and content-encoding metadata identify the compression layer; the record decoder does not guess.

03

The record envelope

A wire v1 record contains exactly the required fields below plus optional sig. Unknown envelope fields are refused. rh is required on read and computed last on construction.

FieldTypeWire v1 rule
vintegerExactly 1; this is the wire grammar version.
linstringNon-empty lineage identifier. Producers use a ULID.
ordinteger0 through 253−1; dense within the lineage.
prevnull or stringNull exactly at ordinal 0; otherwise 64 lowercase hex SHA-256 characters.
atnumberFinite Unix-seconds claim; signed content, never an ordering input.
kstringNon-empty record kind.
observerstringNon-empty producer/observer label under the record-kind profile.
originstringMay be empty; opaque origin label.
bodyobjectA JSON object canonicalizable under JCS.
sigstringOptional and non-empty. Absent means unsigned; null is forbidden.
rhstring64 lowercase hex characters; MUST recompute from the record.

Live-file reference order

The branch’s file emitter writes keys in this human-readable order: v, lin, ord, prev, at, k, observer, origin, body, sig, rh. sig is omitted when absent. This order is a transport convention; hashing uses JCS and therefore does not depend on input key order.

Canonical interchange order

The canonical export profile arrival-jcs-jsonl-v1 emits the RFC 8785 JCS bytes of the complete validated record, including rh, followed by LF. JCS therefore selects recursive object order, number spelling, string escaping, and whitespace. The existing decoder accepts both the readable live-file order and this canonical interchange order; they commit the same logical record.

04

Core body profiles

These profiles document the branch envelope — the triage input. Under the ratified wire v1 (decision:design/arrival-wire-v1-seam-triage), fact, batch, and tick bodies drop the duplicated t discriminator (the envelope k is the one spelling), and the tick record’s observer receives an honest spelling still to be ruled.

genesis

A live-store genesis body contains protocol (integer 1), lineage (exactly equal to lin), and key (a base64 encoding of a raw 32-byte Ed25519 public key). It appears at ordinal 0, has prev: null, and carries sig.

key

A key-introduction body contains observer and key. The named observer is the identity the new raw-32-byte Ed25519 public key may speak for. The outer record carries a signature resolvable to a key valid before this ordinal.

fact

The body is the existing canonical fact codec object. It contains t: "fact", then string fields id, kind, observer, origin, and payload, plus finite numeric ts. An optional inner signature preserves the fact-domain signature. None of the required fields may be null.

batch

The body contains exactly t: "batch" and rows. Rows is an array of at least two complete fact objects in emission order. Batches do not nest, do not contain ticks, and do not repeat a fact ID within one batch. A one-row ceremony uses fact; there is no second spelling as a one-row batch.

tick

The body is the canonical tick codec object: t: "tick"; string fields id, name, origin, and payload; finite numeric ts; nullable numeric since; nullable string fields prev_hash, window_start, fact_cursor, and window_hash; and optional inner signature.

The v1 seams — ruled

The draft bundled three seams here as “preserved for compatibility”; decision:design/arrival-wire-v1-seam-triage ruled them individually. The duplicated discriminator (body.t beside the outer k) DROPS — the fact commitment covers (kind, ts, observer, origin, payload), no t, so no preserved signature is invalidated. The tick writer’s name-as-observer is RE-SPELLED — a name is not an authorship claim; the exact spelling is the open sub-ruling. The inner fact-domain signature beside the outer arrival-content signature KEEPS — two subjects (author content, custody record), a principled pair rather than a seam.

05

Canonicalization and hashes

Every hash input is serialized with JSON Canonicalization Scheme (JCS), RFC 8785. JSON object input order and insignificant whitespace therefore do not affect the commitment. String values, array order, numeric value, field presence, and null do.

rh = lowercase_hex( SHA-256( JCS(record with "rh" removed) ) )

The hash input includes v, lineage, ordinal, predecessor, authored time, kind, observer, origin, body, and optional sig. It excludes only rh, which cannot cover itself. At ordinal n > 0, prev must exactly equal the preceding record’s rh.

Numeric domain

Integers MUST be in the JCS interoperable range −(253−1) through 253−1. Floating-point values MUST be finite. NaN, positive or negative infinity, and numbers that cannot be represented by the selected JCS implementation are refused before hashing.

What the record hash is not

rh is not a checksum of the physical JSON line, database file, page, or table. A harmless reformatting can produce different line bytes with the same logical hash. Canonical export removes that freedom and emits one preferred byte spelling.

06

Signatures and key material

The outer signature commits only the five authored-content fields:

commitment = lowercase_hex( SHA-256( JCS({ k, at, observer, origin, body }) ) )

Coordinate, predecessor, record hash, and signature are excluded. This is deliberate: a source signature remains verifiable when a custodian assigns a different lineage and ordinal. Custody is secured by the record chain and external head witness, not by pretending the author selected the final storage position.

ValueWire representationValidation
Public keyStandard base64, raw 32-byte Ed25519 keyDecode strictly; exactly 32 bytes.
SignatureNon-empty string; base64 in the Ed25519 profileVerify under the selected domain and resolved key.
Digest64 lowercase hex charactersRecompute from JCS; do not trust sender.

Wire grammar treats sig as opaque so cryptographic profiles can evolve independently. A deployment profile MUST pin algorithm, key encoding, signature encoding, and domain-separation string before it treats authorship as verified.

08

Streaming and resume

The portable resume token is a head tuple, not a byte offset. A consumer retains (lineage, ordinal, record_hash), asks the source for records after that head, and verifies the first successor’s lineage, ordinal, and prev before advancing.

  1. Capture and persist the last fully processed head.
  2. On resume, ask the source to prove that exact coordinate still has the same hash.
  3. If it does, stream from ordinal + 1 and verify every link.
  4. If it is absent, lower, or different, report rollback or fork; never silently restart as if this were mere staleness.

A file adapter MAY retain a validated byte offset beside the portable token as a seek optimization. The offset is trusted only when the record ending there matches all three portable head fields. Database cursors, page IDs, row IDs, and LSNs are likewise backend-private hints.

09

Canonical export and manifest

A canonical export captures one head, scans genesis through that head, validates every stored rh, and emits JCS(complete_record) + LF under the arrival-jcs-jsonl-v1 profile. For the same logical prefix and profile, conforming exporters MUST produce identical uncompressed bytes. A file backend re-encodes its records for export; it does not merely copy its readable live-file lines.

Manifest claims

  • Manifest format version and Arrival wire version
  • Lineage, exported ordinal, and exported record hash
  • Total record count and optional per-kind counts
  • SHA-256 digest and byte length of the uncompressed stream
  • Export time as metadata, never as ledger order
  • Optional head attestation or reference to an external witness receipt
Physical digest in its proper place

The export-file digest answers “are these archive bytes unchanged?” The record head answers “which logical history is this?” Both are useful, and neither should be misrepresented as the other.

10

Validation order and resource limits

A streaming importer validates in this order so bad input fails before mutation:

  1. Transport encoding, framing, and configured decompression limits
  2. JSON object shape with duplicate-key rejection
  3. Known fields, required fields, types, nullability, and numeric domain
  4. Body profile for the declared record kind
  5. Record-hash recomputation
  6. Genesis placement or successor lineage, ordinal, and predecessor
  7. Required authorship verification and application admission policy
  8. Atomic append to the destination

Implementations MUST expose configured maximum line size, body nesting, batch row count, total import size, and decompression ratio. The base protocol does not invent a universal small limit that would reject legitimate archives, but “unbounded” is not a conforming security posture. A limit failure is a clean refusal with no partial record.

Unicode

JSON strings are Unicode scalar sequences as interpreted by the JSON and JCS profiles. Wire v1 does not apply additional Unicode normalization: canonically equivalent human text with different code-point sequences remains different content. Identifiers and authorization names that need stronger equivalence rules must define them in their application profile before signing.

11

Evolution and registration

The outer v versions the wire grammar. The genesis body’s protocol versions ledger semantics. A v1 reader refuses an unsupported outer version rather than guessing compatibility. Backends may store several wire versions only when they can unambiguously select and verify the correct codec per lineage.

A future wire version that changes the signature commitment, adds domain separation to rh, or changes body representation necessarily produces different record hashes. It therefore needs a new lineage or a formally specified transition record and cannot masquerade as an in-place schema upgrade.

Deferred registry work

A final filename convention, media type, extension-kind registry, cryptographic profile identifier, and executable golden corpus should be ratified alongside the first independent backend. Until then, .arrival and “Arrival JSONL v1” are project conventions rather than an external standards registration.
