Session wrap-up · architecture suite

Arrival, unbound from storage

Arrival is a logical, append-only custody protocol. A .arrival file is one useful encoding and backend—not a second copy every store must keep.

Ratified 1.0 target Five linked study documents 26 August 2026
01

The decision in one page

The durable idea is not “every store has an arrival file.” It is “every lineage has an ordered, verifiable arrival history with one authoritative append head.” The storage engine may be a local file, DuckDB, PostgreSQL, or a future service, provided it implements the same ledger contract.

Ratified

Ratified 26 August 2026 as the 1.0 full-break target — decision:design/arrival-backend-neutral-protocol — with one amendment: the envelope pins as wire v1 only after the seam triage of decision:design/arrival-wire-v1-seam-triage. The remaining review findings are dispositioned in decision:design/arrival-suite-review-dispositions.

Core invariant

At any moment, one lineage has exactly one designated authority. Exports and replicas are copies of that authority unless an explicit re-custody ceremony says otherwise.

What becomes stable

  • Lineage and dense ordinal coordinates
  • Record semantics and hash chaining
  • Atomic compare-and-append behavior
  • Deterministic scan and portable export
  • External head attestations

What remains replaceable

  • Physical files, pages, tables, and indexes
  • Projection strategy and query language
  • Single-user versus team deployment
  • Local versus remote durability mechanics
  • Transport and archive packaging

This removes the forced double-storage shape. A personal DuckDB store can be the canonical Arrival backend and expose Quack-friendly read views. A team service can use PostgreSQL as its canonical backend. Either one produces a .arrival stream only for interchange, audit, backup, or migration.

Important separation

Query interfaces do not get ledger-write authority. Raw SQL may inspect a DuckDB or PostgreSQL projection, but protocol writes pass through admission and compare-and-append. This is an integrity boundary, not merely an API preference.

Backend selection is explicit in a store descriptor. A filename suffix never silently decides which implementation is authoritative.

Team tenancy

A service backend may host many lineages. One lineage per team gives the clearest authority, export, retention, and access-control boundary. A shared multi-tenant lineage is possible, but it couples authorization and erasure policy across tenants and should require an explicit protocol profile rather than an incidental team_id column.

05

Integrity without hashing the physical database

Hashing an entire database file is useful for identifying one backup image, but it is a poor logical integrity contract: page layout, vacuuming, indexes, statistics, and engine metadata can change while the facts do not. Arrival instead hashes the stable logical record sequence.

Security boundary

A backend administrator can always rewrite storage they fully control. Detection becomes meaningful when a previously seen head—or its signed attestation—is kept outside that administrator’s rewrite boundary: a client cache, another machine, an append-only notary, or several witnesses.

06

The full-break migration

The clean break is an advantage if legacy knowledge stays in one sidecar. The new application need only understand the Arrival interfaces; it never needs a permanent compatibility mode or a dual-write period.

  1. Freeze and inventory. Open the old 0.x store with a frozen reader and capture a stable logical inventory.
  2. Stage a chosen backend. Create a new lineage in a temporary File, DuckDB, PostgreSQL, or service authority.
  3. Stream through the protocol. Translate legacy facts and ticks into record drafts and append only through ArrivalSink.
  4. Prove equivalence. Compare counts, IDs, content commitments, and the deterministic portable export; retain a migration report.
  5. Witness and publish. Sign or retain the new head, then atomically replace the store descriptor that names the authority.
  6. Archive the source. Keep the old store read-only until the chosen rollback window ends; never let both accept writes.
Simplification

Migration targets the protocol, not each storage layout. Adding a DuckDB backend does not require a DuckDB-specific legacy migrator; it requires one backend adapter and the same sidecar pipeline.

07

Decided and still open

Strongly decided

  • Arrival is a protocol, not a mandatory file.
  • One authority exists per lineage.
  • Wire v1 is pinned — body.t dropped, the tick observer re-spelled to the log's custodian, the dual signature kept, and a batch's rows held to one observer (decision:design/arrival-wire-v1-seam-triage).
  • Ledger and query APIs remain separate.
  • The sidecar owns legacy interpretation.
  • External state is required for rollback detection.

Requires a later ruling

  • Tick outer signatures — deferred on purpose, so the tick's custodian label is currently a true but unverified claim
  • Formal authority-transfer / re-custody ceremony
  • Erasure and privacy profile
  • Witness topology and retention policy
  • Extension-kind registry and compatibility rules
  • First production DuckDB and PostgreSQL schemas
  • Multi-tenant lineage policy

None of those open choices undermines the central split. They are profiles built on top of a backend-neutral ledger rather than reasons to make one file format universal.
