2: 
3: Status: draft for native reconciliation and Fable 5.1 **high** design review;
4: implementation has not started. Baseline `ef8b21b2` on `arrival/finish` includes

10: ## Decision and scope
11: 
12: A continuing boundary keeps its recorded consumption history. An ordinary
13: declaration edit changes the current interpretation of facts; it does not
14: restart that boundary. The proposed identity for this supported subset remains
15: the exact local vertex name, boundary role, and boundary name. No declaration
16: hash, file path, projection generation, or new wire identifier becomes identity.
17: 
18: The recommended policy is **inherit for in-place edits**. A trigger/count,
19: condition, fold, parse, route, or dispatch edit keeps the existing tick edge.
20: This is an explicit interpretation policy, not a claim that the old tick would
21: have fired under the new rules. A pending fact already consumed by that edge
22: does not become eligible again just because a declaration changed.
23: 
24: Whole-loop retirement followed by same-name recreation needs separate evidence
25: when an old local tick exists. A tick whose loop/vertex role was ambiguous when
26: received also cannot become unambiguous through a later configuration edit.
27: Those cases refuse supported runtime execution. Facts, ticks, and declarations
28: remain available as evidence; no prior row is changed or relabeled.
29: 
30: The user has been offered a choice between inherited in-place trigger/count
31: edits and a stricter interim refusal of those edits. No answer has arrived as
32: this draft is prepared for review; root proceeds with the recommended inherit
33: policy as a stated assumption. Any later answer and the adversarial design
34: review must be reconciled before implementation. Credential requests and persisted bindings (D0/D2), explicit
35: same-name restart/carry ceremonies, and durable vertex IDs are separate work.
36: 
37: ## What the implementation actually does today
38: 
39: `Vertex.hydrate_snapshot` re-folds captured facts under the current declaration
40: in receipt order. It does **not** deserialize an old tick payload as current
41: fold state. A local loop tick invokes `Loop.replay_boundary`: reset to the
42: current initial state when reset is enabled, clear repeating-count bookkeeping,
43: or mark a one-shot boundary exhausted. A local vertex tick restores the vertex
44: period timestamp and does not reset every loop.
45: 
46: `plan_pending_boundaries` selects the greatest event-time/receipt edge per local
47: tick name. Facts at an equal timestamp precede or follow that edge by receipt
48: coordinate. This remains distinct from the tick's fact cursor and from
49: declaration receipt ordering. Count boundaries remain ingress-driven.
50: 
51: The grammar currently exposes `when`, `after`, and `every`; its compiler always
52: sets loop-boundary `reset=True`. The lower-level `Loop` supports carry, but
53: there is no public declaration reset/carry edit to implement in C6. Fold
54: overrides replace initial state and fold code, not declared boundary reset.
55: 
56: Consequently an in-place `every 5` to `every 10` edit starts its next count from
57: the retained recorded boundary. An edit to `after` when a recorded tick exists
58: inherits an already-consumed one-shot boundary. A user wanting it to fire again
59: is requesting a restart; C6 does not silently provide one. Historical payloads
60: keep their original meaning and bytes even when current replay differs.

67: ## Contract matrix
68: 
69: | Situation at the bounded head | Supported result |
70: | --- | --- |
71: | Same continuously present loop, unchanged declaration | Inherit its recorded reset/count/period and pending consumption evidence. |
72: | Same continuously present loop, edited fold/parse/routes/trigger/count/conditions/run or presentation | Inherit the same edge and replay under the new interpretation; no implicit restart. |
73: | No local ticks for a loop; edit, remove/recreate, or introduce a boundary | Allowed, subject to existing checks. Older facts may replay and pending triggers may become eligible; this is not a fresh-facts cutoff. |
74: | Remove a loop that has old ticks | Allowed when it is absent from the proposed runtime. Preserve old ticks as evidence. |
75: | Reintroduce that retired runtime name after it had a local tick | Refuse ordinary declaration preparation/preview and runtime capture. A final-document comparison alone cannot detect this. |

82: | Explicit restart, state carry, alias, or same-name incarnation cutover | Deferred new protocol behavior; not inferred from an ordinary edit, projection rebuild, or locator move. |

90: ## History and evidence algorithm
91: 
92: The shared validator is pure over one captured declaration anchor, complete
93: self-lineage declaration fact history, bounded ticks, and the target document
94: set (effective current state for runtime, proposed successor for editing).
95: It does not open a store, sign, read keys, consult external source files or the
96: environment, repair projections, or execute any source/dispatch command.
97: 
98: 1. Validate the declaration anchor against the captured full H through the
99:    existing custody/projection contract. Select only the own genesis and
100:    self-lineage declaration overlays. Foreign and unscoped declarations remain
101:    inert, matching the existing resolver. Sort by receipt ordinal and sequence,
102:    never authored time or fact ID.
103: 2. Reconstruct effective runtime names at the genesis and each committed
104:    declaration revision. Preserve retirement evidence across intermediate
105:    revisions; do not compare only genesis/current or before/proposed documents.
106:    Multiple declaration documents in one Arrival batch form one revision:
107:    evaluate the resulting effective set, not transient partial document states
108:    with no observable runtime between them. This grouping is for namespace
109:    continuity; document overlay order remains receipt-sequence order.
110: 3. At each owned tick's receipt position, classify its role using that revision.
111:    A vertex-name tick with a simultaneously present loop of that name is
112:    ambiguous. A currently relevant loop-name tick with no provable historical
113:    loop membership is unproven. Tick payload shape, signature, cursor, or
114:    current name validity cannot recover the missing role evidence.
115: 4. For each target runtime name with historical local ticks, require continuous
116:    membership since the relevant tick. A disappearance and later return
117:    conflicts even if its final declaration equals the earlier one. Internal
118:    tracking of membership intervals is evidence analysis, not a newly minted
119:    persistent incarnation ID. Ignore retired names that the target does not
120:    interpret, except that an ambiguous vertex-name tick still affects the
121:    retained vertex identity.
122: 5. Analyze the proposed successor as one additional revision with no fabricated
123:    fact ID, timestamp, ordinal, or Commit. This allows retirement and safe
124:    configuration correction even when the old runtime itself refuses.
125: 6. Return normally or a deterministic diagnostic naming the reason, boundary,
126:    and actual conflicting tick/declaration receipt where available. Do not
127:    manufacture an epoch/cutoff or report guessed identity as proven.
128: 
129: The evidence read is through captured H even when event timestamps are negative
130: or far in the future. `TickRequest` defaults to `since=0`; the validator must
131: explicitly request the full timestamp range. Existing hydration/pending
132: timestamp selection is a separate policy and must not be widened accidentally.
133: 
134: Unchanged wire declaration decoding remains authoritative. Prefer sharing the
135: existing overlay step/ordering code rather than introducing a second subtly
136: different definition of self-lineage history. Unknown declaration kinds retain
137: the resolver's forward-compatible inert treatment; malformed supported
138: namespace evidence refuses rather than yielding a fabricated safe history.

140: ## Generated loop names
141: 
142: Only template sources with a declared `loop` generate runtime loop specs in
143: the current compiler. Bare paths, inline source commands, and templates without
144: such a loop do not create additional loop identities. They must not trigger a
145: blanket source-history refusal.
146: 
147: For a template loop, literal inline parameter rows and the stored loop document
148: can establish generated names without opening the template file. Match the
149: compiler's actual ordering and override semantics: sources sorted by recorded
150: order/subject, parameter rows in order, generated specs overriding explicit
151: specs at equal names. Variables used only by collection commands do not make a
152: literal loop name unprovable.
153: 
154: A `from` parameter file contains rows not stored in the declaration; its hash
155: pin establishes current drift checking, not historical row values. An
156: environment-indirected `kind` similarly lacks a recorded old value. Those
157: sources can generate/override unknown names, including the vertex name. A
158: historical owned tick during such an unresolved revision cannot be assumed to
159: have had an unambiguous role. Unchanged source text does not fix this gap.
160: 
161: Use three-valued membership per name and revision. Direct, implicit, or literal
162: generated membership proves **present** even if another generator has unknown
163: names: an override changes its interpretation but does not remove that name.
164: If the name is not in the provable set and an unresolved generator could emit
165: it, membership is **unknown**. Otherwise it is **absent**.
166: 
167: For every old local loop tick that the target would interpret, membership must
168: be provably present at its receipt and throughout all later revisions through
169: the target. Unknown membership anywhere in that interval refuses: an unknown
170: intervening revision could conceal retirement/recreation without containing a
171: tick itself. Analyze every relevant tick, not just the newest pending edge;
172: hydration also consumes historical reset markers. A tick whose name is absent
173: from the target is not attached to a current loop, so that retired stream alone
174: does not block execution. Unknown target membership for an old tick refuses.
175: 
176: For a vertex-name tick, loop membership at its receipt must be provably absent.
177: Present means a role collision; unknown means its role cannot be established.
178: The vertex identity itself continues while its boundary list is edited or
179: disabled, so only loop-name ambiguity at that tick changes this role proof.
180: Unresolved revisions before all relevant ticks do not, by themselves, create
181: consumption obligations. This is a conservative evidence rule, not proof that
182: unknown expansions actually collided. Literal generated sources and provably
183: continuous direct loops must remain usable. Do not compile old declarations
184: against current external inputs or claim that no document edit proves stability.

1: # C6 engine design notes: boundary continuity across declaration history
2: 
3: Status: design for cross-model review. No implementation is authorized by this
4: document. It assumes C3 custody completion and the accepted C5 current-name
5: reservation are already present.
6: 
7: ## Decision to make
8: 
9: D5 says a declaration edit changes interpretation without rewriting facts, while
10: an unchanged boundary identity keeps its established consumption edge. Restart
11: and reincarnation must be explicit; a declaration hash is not a boundary ID
12: ([identity decisions D5](identity-decisions-2026-09-06.md#d5--declaration-edits-preserve-history-reset-must-be-explicit)).
13: C6 exists because the current runtime cannot distinguish a continuously defined
14: loop from a retired and later recreated loop that happens to reuse its name
15: ([consistency matrix C6](consistency-contract-matrix-2026-09-06.md#prioritized-worklist)).
16: 
17: The bounded policy proposed here is **inherit by runtime role and name while the
18: role remains continuously present**:
19: 
20: - A loop is `(vertex name, loop role, loop name)`. In-place edits retain that
21:   identity and its last recorded edge. This includes changing `when`/`after`/
22:   `every`, counts, matches, conditions, folds, parse, routes, run commands and
23:   read facets. Those changes can alter current and future conclusions; that is
24:   the append-forward reinterpretation D5 already permits.
25: - Retiring the whole loop ends its presence epoch. Recreating the same name may
26:   reuse an earlier epoch's local tick under the current implementation. Refuse
27:   the recreation when such a tick exists. A tick-free retirement/recreation is
28:   permitted: facts alone are interpretation input and make no persisted claim
29:   that a boundary was consumed.
30: - A vertex boundary is `(vertex name, vertex-boundary role)`. Its several trigger
31:   clauses all produce the same tick name and share one vertex-period edge.
32:   Editing the clause tuple, including empty then nonempty, retains the role; it
33:   is not treated as a new incarnation.
34: - A historical local tick whose role was ambiguous when received is not repaired
35:   by a later C5 configuration correction. In particular, if `origin == name ==
36:   vertex` and a same-named loop existed at that receipt coordinate, a current
37:   vertex boundary cannot safely consume it as a vertex-period edge. A repair
38:   with no such tick is valid. Removing the vertex-boundary consumer as well as
39:   the colliding loop leaves the ambiguous row available for inspection but out
40:   of runtime state.
41: 
42: This is intentionally narrower than semantic equivalence. It does not try to
43: prove that two folds or predicates compute the same result.
44: 
45: ## What the engine actually does
46: 
47: ### Recorded ticks are edges, not state checkpoints
48: 
49: `Vertex.hydrate_snapshot` merges facts and ticks by receipt coordinate. For an
50: owned tick (`tick.origin == vertex.name`), it looks up the **current** loop by
51: `tick.name`, calls `Loop.replay_boundary`, and independently treats
52: `tick.name == vertex.name` as a vertex-period edge
53: ([vertex.py:769](../../../libs/engine/src/engine/vertex.py#L769),
54: [vertex.py:784](../../../libs/engine/src/engine/vertex.py#L784)). It never reads
55: the old tick payload, `since`, fact cursor, window hash or signature into fold
56: state.
57: 
58: `Loop.replay_boundary` applies the **current** loop's reset/count mode: reset
59: returns the current projection to its current initial value, `every` zeros the
60: count, and `after` marks it exhausted
61: ([loop.py:157](../../../libs/engine/src/engine/loop.py#L157)). Therefore an old
62: edge under a current `after` definition means “already exhausted”; under a
63: current `every` definition it is the edge from which the new count resumes.
64: That result should be explicit in tests, rather than described as preservation
65: of the old trigger policy.
66: 
67: Facts are always routed, parsed and folded under the current candidate
68: ([vertex.py:821](../../../libs/engine/src/engine/vertex.py#L821)). This is why a
69: fold-only edit is not an “incompatible tick payload” in today's engine: no tick
70: payload is deserialized. Historical tick payloads remain raw evidence. If a
71: future runtime hydrates from payload checkpoints, it will need a persisted
72: checkpoint schema/compatibility claim and is outside this slice.
73: 
74: ### Pending boundaries use the same name edge on a different ordering axis
75: 
76: Source-mode pending evaluation builds the latest owned edge per tick name using
77: event time with receipt coordinate as its tie-break, then scans eligible facts
78: by event time and receipt coordinate
79: ([vertex.py:1260](../../../libs/engine/src/engine/vertex.py#L1260)). This is
80: correctly distinct from the declaration-history question: which definition was
81: in force at a tick is determined by the tick's **receipt coordinate**, not its
82: event timestamp. The validator must not replace either ordering with the other.
83: 
84: Count boundaries are not invented by pending evaluation
85: ([vertex.py:1275](../../../libs/engine/src/engine/vertex.py#L1275)); their restored
86: counter/exhaustion state comes from hydration
87: ([vertex.py:835](../../../libs/engine/src/engine/vertex.py#L835)). A continuity
88: guard must therefore run before both ordinary planning and source pending
89: planning.
90: 
91: ### The supported declaration surface currently has reset only
92: 
93: The generic engine permits `reset=False`, but historized `LoopDef` has no reset
94: field ([ast.py:518](../../../libs/lang/src/lang/ast.py#L518)). Every DSL boundary
95: maps to `reset=True`, and materialization copies that value into `Loop`
96: ([compiler.py:541](../../../libs/engine/src/engine/compiler.py#L541),
97: [compiler.py:981](../../../libs/engine/src/engine/compiler.py#L981)). The
98: programmatic carry form is therefore not a supported Arrival declaration
99: transition today.
100: 
101: No reset/carry field should be invented in C6. If one is added later, changing
102: it in the presence of an earlier local tick must require the explicit transition
103: ceremony: otherwise `replay_boundary` retroactively applies the new choice to
104: every old edge. Low-level callers that construct a detached `Vertex` remain
105: caller-responsible; the supported Arrival authority path reconstructs from
106: historized documents.
107: 
108: ### Final effective documents are insufficient
109: 
110: The snapshot declaration resolver seeds the genesis document set, applies own-
111: lineage definitions/tombstones in receipt order, and returns only the surviving
112: documents ([declaration.py:221](../../../libs/engine/src/engine/declaration.py#L221)).
113: That correctly answers “what is effective now,” but erases the retirement that
114: distinguishes continuous presence from reincarnation.
115: 
116: Runtime construction fetches all internal facts, resolves only the final set,
117: compiles/materializes a new candidate, then hydrates it with ticks
118: ([runtime_write.py:715](../../../libs/engine/src/engine/runtime_write.py#L715)).
119: Declaration preparation currently requests declaration facts only, resolves the
120: final set, diffs the proposal and starts signing
121: ([arrival_declarations.py:799](../../../libs/engine/src/engine/arrival_declarations.py#L799)).
122: Both call sites need the same historical analysis before hydration or signing.
123: 
124: ## Proposed bounded implementation
125: 
126: ### 1. Pure receipt-history analyzer
127: 
128: Add a small engine module, tentatively `arrival_boundary_continuity.py`, with no
129: store or registry access:
130: 
131: ```python
132: @dataclass(frozen=True)
133: class BoundaryContinuityIssue:
134:     reason: Literal[
135:         "prior-incarnation",
136:         "ambiguous-tick-role",
137:         "unproven-generated-incarnation",
138:     ]
139:     vertex_name: str
140:     loop_name: str | None
141:     tick_id: str
142:     tick_ordinal: int
143:     tick_seq: int
144:     epoch_started_at: tuple[int, int] | None
145:     retired_at: tuple[int, int] | None
146: 
147: def analyze_boundary_continuity(
148:     anchor: DeclarationAnchor,
149:     facts: Sequence[Fact],
150:     ticks: Sequence[Tick],
151:     *,
152:     effective_loop_names: Collection[str],
153:     has_vertex_boundary: bool,
154:     generated_provenance: GeneratedLoopProvenance,
155: ) -> BoundaryContinuityIssue | None: ...
156: ```
157: 
158: The exact DTO names are not protocol. The useful property is that the analyzer
159: returns structured evidence and does not choose an SDK error. Runtime capture
160: raises `RuntimeWriteRefused` from an issue; declaration preparation uses its
161: existing `DeclarationPreparationRefused` boundary and C2 pre-effect evidence.
162: Both should retain the issue as `cause`, including tick and declaration receipt
163: coordinates. Raw evidence readers, inspection, verification and export do not
164: call the analyzer.
165: 
166: The analyzer:
167: 
168: 1. Validates/uses the already licensed declaration anchor. It seeds state from
169:    the own genesis `documents` and ignores foreign/absent-lineage declaration
170:    rows exactly as the resolver does.
171: 2. Sorts declaration facts and ticks by `(arrival_ordinal, arrival_seq)`. It
172:    applies every declaration fact sharing one `arrival_ordinal` as one atomic
173:    revision before moving to the next record. A wire `batch` contains fact rows
174:    only, so there is no legitimate tick halfway through a declaration ceremony
175:    ([arrival_body.py:179](../../../libs/engine/src/engine/arrival_body.py#L179)).
176: 3. Tracks uninterrupted presence epochs for **all materialized loop names**, not
177:    merely loops that currently declare a boundary. Membership at each atomic
178:    revision is three-valued: present, absent, or unprovable from recorded
179:    template inputs. Hydration calls `replay_boundary` on a matching passive loop
180:    too.
181: 4. Classifies only owned ticks. Foreign and originless ticks remain visible but
182:    establish no local edge, matching `_owns_tick`.
183: 5. For every current loop name, requires every owned matching tick to have a
184:    continuously **present** membership from that tick's receipt through the
185:    target revision. A tick before genesis, during absence, or in an earlier
186:    retired epoch makes the current consumption unproven. So does an unresolved
187:    intermediate revision after an otherwise known tick: it may conceal an
188:    absence/recreation, and the later known definition cannot repair that gap. An
189:    unresolved revision entirely before the latest relevant tick does not matter
190:    if membership is provably present from that tick forward. A current loop with
191:    no such tick is clean and is allowed, even if facts of that kind predate it.
192: 6. If the current runtime has a vertex boundary, checks each owned tick named
193:    for the vertex against the definition state at that tick's receipt. A
194:    same-named loop in force there is an ambiguous role; pre-genesis role is
195:    likewise unproven. If there is no current vertex-boundary consumer, the row
196:    does not block runtime execution, but a proposal that adds one is checked and
197:    refused.
198: 
199: The query must request the full bounded tick prefix, not the convenience time
200: default. `TickRequest()` starts at `0.0`
201: ([arrival_contract.py:248](../../../libs/engine/src/engine/arrival_contract.py#L248)),
202: while wire timestamps are finite but need not be nonnegative. Use
203: `TickRequest(since=float("-inf"))`, keep the snapshot's captured-head bound, and
204: sort by receipt coordinate inside the analyzer. This establishes continuity
205: from the whole receipt prefix. Existing hydration/pending timestamp selection
206: must not be widened as an incidental C6 change; if the runtime keeps its current
207: nonnegative convenience request, name the two tick selections separately and
208: test the negative-time history guard explicitly.
209: 
210: ### 2. Runtime integration before materialization effects
211: 
212: In `_build_effective_arrival_candidate`:
213: 
214: 1. Fetch facts and the complete continuity tick prefix from the same CURRENT
215:    snapshot. Keep any narrower runtime tick selection explicit rather than
216:    silently relying on `TickRequest()` in both roles.
217: 2. Resolve and compile the current declaration, including final template specs.
218: 3. Analyze continuity before `materialize_vertex` and before
219:    `hydrate_snapshot`.
220: 4. Store the already checked facts/ticks in `RuntimeCapture`; ordinary and batch
221:    preparation already compose `capture_runtime`, and source preparation calls
222:    `capture_runtime(source_mode=True)` before collector construction
223:    ([arrival_sources.py:477](../../../libs/engine/src/engine/arrival_sources.py#L477)).
224: 
225: This single chokepoint covers supported ordinary, batch, pending-boundary and
226: source paths. `plan_batch_from_capture` needs no second historical scan because
227: the immutable capture was validated at its exact basis. Later source tiers
228: recapture and already refuse changed declaration documents before collection
229: ([arrival_sources.py:959](../../../libs/engine/src/engine/arrival_sources.py#L959));
230: the new capture performs continuity validation as well.
231: 
232: The guard must run before fold initializers or external collectors. Template
233: compilation already performs pinned source reads in runtime construction, so
234: the bounded slice does not add a second live locator/declaration read.
235: 
236: ### 3. Declaration proposal integration before signing
237: 
238: `prepare_declaration_edit` should fetch all declaration facts and the complete
239: tick prefix from its existing snapshot. After `diff_documents`, simulate the
240: proposal as one next atomic revision and analyze the resulting current runtime
241: roles before building `_declaration_row` or invoking any signer. This preserves
242: C5's append-forward correction rule:
243: 
244: - removing a currently invalid collision is permitted when no recorded tick
245:   makes the remaining vertex role ambiguous;
246: - a collision that did produce an ambiguous tick cannot be “proved repaired” by
247:   merely adding a unique loop;
248: - retirement is permitted; recreation is refused only when the new current loop
249:   would consume an owned tick outside its new epoch;
250: - a never-used name and a tick-free retired name are permitted.
251: 
252: The no-op path should analyze the current state too if it is returned as an
253: executable declaration basis; otherwise a no-op could report a safe plan that
254: runtime capture immediately refuses. The result remains a refusal before intent,
255: cache publication, signing or append. Initialization needs no C6 history check:
256: there is no earlier local tick; C5 proposed-name validation remains its guard.
257: 
258: ### 4. Template-generated names
259: 
260: The runtime final map is direct specs updated by template specs
261: ([runtime_write.py:760](../../../libs/engine/src/engine/runtime_write.py#L760)).
262: Template source documents retain their loop definition, inline parameter forms,
263: and hashes for template/parameter files, but not resolved environment values or
264: old file bytes
265: ([document.py:603](../../../libs/lang/src/lang/document.py#L603)). Compilation
266: loads parameter files and resolves whole-value `$ENV` indirection at runtime
267: ([compiler.py:429](../../../libs/engine/src/engine/compiler.py#L429)).
268: 
269: Consequently the analyzer must not claim it can reconstruct every historical
270: expanded name:
271: 
272: - Literal inline `with kind=...` rows are reconstructible from each recorded
273:   source-document revision. Treat their generated names like direct loops.
274: - An unchanged external parameter-file recipe can be reconstructed only while
275:   the current file verifies against the same recorded hash; an older replaced
276:   hash without retained bytes cannot be reconstructed.
277: - An environment-indirected kind is never historical identity evidence because
278:   its resolved value was deliberately not absorbed. Its generated membership is
279:   unprovable for the entire declaration revision, even if the current expansion
280:   happens to name a known loop.
281: - Source entries with no loop spec do not add loop names and are irrelevant to
282:   this check. Command/cadence-only edits do not create an incarnation.
283: - A direct or implicit loop that is provably present keeps membership present
284:   even while another template's generated-name set is unknown. A generated
285:   override can change the spec, but inherit-by-role/name treats that as an
286:   in-place interpretation edit; the unknown source cannot conceal absence of a
287:   name another recorded definition guarantees.
288: 
289: The bounded safe fallback is refusal only when the current runtime would consume
290: an owned tick whose continuous generated-loop epoch cannot be proven. An
291: unresolved revision at the tick or anywhere after it is such a gap, even if the
292: current revision is known again; otherwise remove/recreate could hide inside the
293: unknown interval. Do not refuse a dynamic template merely because it exists,
294: and do not use today's env or unpinned bytes as yesterday's proof. If compiler
295: work cannot retain enough per-spec provenance without widening the slice,
296: reject the unprovable tick case and leave richer template continuity for a
297: follow-up.
298: 
299: The implicit `cite` loop is also materialized even when undeclared
300: ([compiler.py:1003](../../../libs/engine/src/engine/compiler.py#L1003)). Treat it
301: as a continuously present built-in role for the supported runtime epoch; an
302: explicit `cite` definition changes its interpretation in place rather than
303: retiring its name. A local `cite` tick before the historized epoch remains
304: unproven.
305: 
306: ## Compatibility table
307: 
308: | Transition with current consumer | Local tick evidence | Proposed result |
309: | --- | --- | --- |
310: | Fold/search/preview/edge/lifecycle/run edit | any tick in current presence epoch | allow; current interpretation, same edge |
311: | `when` trigger/match/condition edit | any tick in current presence epoch | allow; pending facts after the edge use new predicate |
312: | `every N` to `every M` | prior loop tick | allow; new count starts at zero after last tick |
313: | `every` to `after` | prior loop tick | allow; current `after` is already exhausted |
314: | `after` to `every` | prior loop tick | allow; current `every` resumes from last tick |
315: | Remove boundary but retain loop | prior loop tick | allow; historical reset edge still partitions current replay |
316: | Remove loop and leave it absent | prior loop tick | allow; no current loop consumes the row |
317: | Remove then recreate loop | no owned tick before new epoch | allow; facts are reinterpreted, no persisted edge is reused |
318: | Remove then recreate loop | owned tick before new epoch | refuse; incarnation is not recorded |
319: | Add never-declared loop | no prior owned same-name tick | allow |
320: | Add apparently new loop | prior/pre-genesis owned same-name tick | refuse; clean identity is unproven |
321: | Repair C5 loop/vertex collision | no ambiguous tick | allow |
322: | Repair collision but retain vertex boundary | ambiguous local vertex-name tick | refuse while vertex boundary would consume it |
323: | Same-name foreign/originless tick | any transition | ignore for continuity; it is not a local edge |
324: | Change reset/carry | earlier local tick | not expressible now; future explicit transition required |

326: ## Acceptance tests for an implementation slice
327: 
328: Use real signed declaration history and a real file projection for the public
329: preparation/capture tests; pure analyzer tests can use small DTO fixtures.
330: 
331: 1. A continuously present `every=2` loop fires, is edited to `every=3`, and
332:    resumes counting from the recorded tick. `every -> after` is exhausted by the
333:    old tick; `after -> every` resumes. These pin inherit-by-name rather than
334:    accidental old-policy replay.
335: 2. Fold-only, condition, route, parse, presentation and run edits with a prior
336:    tick are accepted and deterministically use current interpretation.
337: 3. A boundary is removed while its loop stays passive; hydration still applies
338:    the existing edge. Re-adding the boundary stays the same loop epoch.
339: 4. Whole-loop remove/recreate with an earlier owned tick refuses declaration
340:    preparation before signing and append. The same history without a tick is
341:    accepted even with old facts. Removal without recreation remains executable.
342: 5. An already-recorded/imported unsafe recreation refuses ordinary capture,
343:    batch and source preparation before signing, append, pending tick planning or
344:    collector construction. Handles close through existing capture cleanup.
345: 6. A C5 collision followed by a local ambiguous tick and then a configuration
346:    repair still refuses a current vertex-boundary consumer. The tick-free repair
347:    succeeds. Removing the vertex-boundary consumer leaves evidence reads usable.
348: 7. Passive current loops are included: an out-of-epoch tick refuses even though
349:    the loop declares no boundary. Foreign and originless same-name ticks do not.
350: 8. Multiple declaration changes in one Arrival ordinal are one state transition;
351:    source replacement does not create a false intermediate incarnation.
352: 9. A negative-event-time tick is detected through the full receipt-prefix
353:    request.
354: 10. Static literal generated names get the same epoch behavior. Dynamic/env or
355:     unreconstructible historical generated names refuse only when a current
356:     consumer would reuse their owned tick; a source with no loop is unaffected.
357: 11. Raw read, inspection, verification and exact export still expose histories
358:     that runtime execution refuses.
359: 
360: ## Explicit transition deferred
361: 
362: Refusal is not a restart mechanism. A later append-forward transition needs a
363: reviewed declaration event that says which `(vertex, role, name)` is being
364: continued or restarted and establishes the receipt cutoff for the new
365: incarnation. Hydration and pending evaluation would then select edges within
366: that declared incarnation. The event must also define reset/carry behavior and
367: how an operator adjudicates old C5 role ambiguity. It must not rewrite existing
368: facts/ticks or infer intent from a declaration hash.
369: 
370: That future ceremony may avoid changing the tick wire shape by making the
371: incarnation interval a declaration-history claim, but its vocabulary,
372: authorization, import behavior and recovery semantics require protocol review.
373: C6's first slice should only refuse cases that current evidence cannot classify.
374: 
375: ## Limits to state plainly
376: 
377: - This is a role/name continuity check, not a full projection-vs-ledger audit or
378:   authorship verification pass.
379: - It does not prove semantic equivalence of folds, routes, parse steps or
380:   predicates. D5 permits those to reinterpret facts under the retained edge.
381: - Current declaration history cannot prove old environment values or replaced
382:   external parameter-file contents. The design refuses affected edge reuse
383:   rather than substituting current ingress.
384: - Facts without a tick do not prove a consumed boundary. Allowing their current
385:   reinterpretation may cause a newly declared pending boundary to fire; that is
386:   the requested current interpretation, not a recovered historical claim.
387: - Histories predating declaration genesis have no definition timeline. A current
388:   role must not consume a pre-genesis local tick unless a later explicit
389:   transition classifies it.
390: - Generic/legacy `Vertex` construction and evidence-only reads retain their
391:   current behavior. The guard belongs to supported Arrival authority planning
392:   and declaration preparation.

1: # C6 SDK boundary continuity design notes
2: 
3: ## Finding
4: 
5: The supported Arrival writer captures effective declaration documents, facts,
6: and ticks at one CURRENT basis, then hydrates a detached runtime
7: ([runtime_write.py](../../../libs/engine/src/engine/runtime_write.py#L719-L850)).
8: Hydration treats every tick with `origin == effective vertex name` as local and
9: applies a matching tick name to the current loop, even when that loop is
10: passive ([vertex.py](../../../libs/engine/src/engine/vertex.py#L769-L819)). An
11: in-place declaration edit therefore reuses its old tick's reset/count/period
12: effect by policy. A vertex tick has the
13: same name as the vertex, so a historical C5 collision (`origin == name` and
14: `tick.name == name`) cannot be classified after a later declaration correction.
15: 
16: This is not a reason to restrict ordinary interpretation. Facts are deliberately
17: re-folded under the bounded effective declaration; hydration does not restore
18: old tick payloads as fold state. Existing `diff_documents` already rejects a
19: vertex rename as a normal declaration edit
20: ([document.py](../../../libs/lang/src/lang/document.py#L1100-L1157)). C5
21: separately rejects a *current* loop/vertex name collision. C6 is about historical
22: tick consumption, not credentials, observer equivalence, key locations, or
23: lineage identity (D0/D2 remain separate).
24: 
25: ## Proposed public policy
26: 
27: Use the effective declaration and complete bounded tick stream at the
28: declaration/runtime capture head. Only ticks owned by the effective vertex
29: (`origin` exactly equals its declared name) participate; foreign or originless
30: ticks remain evidence and never block a transition. Compare names exactly.
31: 
32: The supported identity is the exact `(vertex name, boundary role, boundary
33: name)` and its continuous membership interval, rather than a declaration or
34: boundary fingerprint. An in-place trigger/count, condition, fold, parse, route,
35: or dispatch edit inherits that identity's recorded edge. The current compiler
36: fixes `reset=True` for all DSL boundary forms
37: ([compiler.py](../../../libs/engine/src/engine/compiler.py#L541-L593)); if reset
38: or carry becomes declarative later, changing it is an explicit-transition
39: question, not an inferred identity change. Source, search, presentation,
40: lifecycle, and observer edits remain ordinary interpretation changes.
41: 
42: Generated source loops need a stricter evidence rule. Only a template source
43: with a declared `loop` can generate additional runtime loop identities; bare
44: paths, inline collection commands, and templates without `loop` do not. Literal
45: inline parameter rows plus the absorbed loop document can establish generated
46: names. A `from` parameter file or environment-indirected kind cannot: its hash
47: pin proves current drift checking, not past values. If an owned local tick
48: occurs during such an unresolved revision, continuity is **unprovable** for the
49: affected runtime capture or plan even when today's source document is unchanged.
50: Do not load current environment/files as history. A command-only source edit is
51: ordinary when full history proves its generated name literal and stable; it
52: does not itself reset a boundary.
53: 
54: | Proposed change at captured H | Historical owned tick for scope/name? | Result | User-visible route |
55: | --- | --- | --- | --- |
56: | Same continuously present loop or vertex boundary; fold, parse, route, trigger/count, condition, run, or presentation edit | either | **Inherit** existing tick edge/count/period. Facts may be reinterpreted under the new declaration; this is not a restart. | Existing `plan_kind_mutation`, `add_kind`, `edit_kind`, `edit_declaration`. |
57: | Add/change a boundary, or recreate a loop with a name that has no owned tick | no | **Inherit interpretation**, including re-folded older facts. This is not a fresh-facts cutoff. | Existing declaration edit APIs, after normal preview/CAS. |
58: | Remove a loop entirely | either | **Retire** it from future runtime; its facts/ticks remain queryable evidence. | Existing `remove_kind`; a later same-name add is subject to the reappearance rule below. |
59: | A runtime name with owned ticks disappears and later reappears, or a loop is disabled while the same runtime name remains | yes | **Refuse** ordinary plan/apply/runtime capture. Do not guess reset, carry, or tick role. | Choose a fresh name for a distinct future identity, or use a future explicit transition. |
60: | C5-collision configuration with no owned tick | no | **Repair forward** by a normal declaration edit that removes/renames the colliding loop. | Existing declaration edit; C5 already permits preparing a collision-free successor. |
61: | C5-collision history with an owned ambiguous tick | yes | **Refuse runtime**, even after a later collision-free declaration. Reads, inspection, verify, export, and declaration evidence remain available. | A future explicit cutover is required; configuration-only repair cannot classify the old tick. |
62: | Source/template-generated identity cannot be reconstructed from absorbed history and an owned tick exists | yes | **Refuse** the affected runtime capture or declaration plan, even if the current source declaration is textually unchanged. | Preserve declaration/tick evidence; a future durable transition or historically recorded expansion is required. |
63: 
64: Retiring an old loop and adding a fresh, unique loop name creates a distinct
65: future tick identity. It is **not** a restart: it neither cuts off old facts nor
66: promises that a new interpretation will not fold or fire on them. It does not
67: carry state or translate old facts/ticks. A current C5 collision with no tick
68: can use that configuration repair. A collision that already produced a tick
69: cannot be made executable by merely renaming a later loop because that row is
70: also shaped like a vertex period tick.
71: 
72: ## Explicit transition, deferred implementation
73: 
74: The alternative is a new signed declaration-ceremony transition, for example
75: `plan_boundary_transition`/`apply_boundary_transition`, rather than an option
76: silently attached to `edit_kind`. It would atomically append the successor
77: declaration documents and a durable transition fact at one exact H. Its body
78: must name the scope (loop or vertex), old/new names, action (`restart` or
79: retire), predecessor evidence, and its effective receipt coordinate. Runtime
80: capture would reconstruct declaration transitions
81: from the bounded declaration stream and ignore pre-cutover tick consumption for
82: the transitioned scope. The result exposes captured H, transition fact ID,
83: Commit/outcome, and post-commit projection status just as declaration edits do.
84: 
85: That does not change the tick wire format, but it is new declaration vocabulary
86: and replay behavior. It needs a separate compatibility decision for historical
87: reads and for vertex-boundary restarts; it must never relabel old ticks. Until
88: then, do not expose a `reset`, `carry`, same-name recreation, or alias parameter
89: on the existing SDK edit APIs.
90: 
91: ## Entry-point worklist
92: 
93: 1. Extract a pure continuity classifier over `(full bounded declaration
94:    history through H, proposed-after, bounded owned ticks,
95:    source-expansion proof)`. It must reconstruct exact role/name membership
96:    intervals across retired/recreated/imported history, not compare only
97:    effective-before/effective-after documents. Use it in
98:    `prepare_declaration_edit` and `_arrival_semantic_preview`; plans report the
99:    reason before draft/signature use. Initialization has no pre-genesis history,
100:    so C5's existing new-declaration validation is sufficient there.
101: 2. Run the same classifier in `capture_runtime`, ordinary/batch preparation,
102:    and source invocation preparation. A local cache cannot bypass a historized
103:    unsafe transition. Its tick input must explicitly request
104:    `TickRequest(since=-inf, until=inf)`: the contract default is `since=0`,
105:    which is not a complete historical range. Preserve C5's current-name
106:    validator as a separate check.
107: 3. Keep `preview_emission`, `emit_fact`, `emit_batch`, and `run_sources` on the
108:    existing normalized pre-append refusal path. Credential providers may load
109:    existing signer callables before capture, but no signer invocation,
110:    collector, append, or maintenance action begins after a continuity refusal.
111: 4. Leave `read_facts`, summary, state, timeline, inspection, verify, and export
112:    usable for unsafe histories. They return their normal bounded basis/evidence;
113:    none claims runtime execution is safe.
114: 
115: `capture_runtime` already opens `ProjectionRequirement.CURRENT`; so do ordinary,
116: batch, preview, and source paths that delegate to it. SDK
117: `_arrival_semantic_preview` also uses `_open_arrival_read(... CURRENT)` and
118: must pass that snapshot's complete `_decl` facts plus full-range ticks to the
119: pure classifier. `prepare_declaration_edit` likewise has a CURRENT snapshot
120: and all declaration facts but must add the explicit full-range tick request.
121: No C6 decision needs `ALLOW_BEHIND`, a legacy reader, or a second snapshot.
122: 
123: ## Acceptance scenarios
124: 
125: - A loop with an owned tick accepts fold-only and count/when/match edits, then
126:   emit/preview resumes with the preserved boundary edge. It does not refire a
127:   previously consumed observation under the new rule.
128: - Removing a ticked loop succeeds; adding the same name later refuses. A
129:   fresh-name successor has a distinct future tick identity, without claiming a
130:   fact cutoff, reset, or state carry.
131: - A new boundary on a tick-free loop is accepted and its first capture states
132:   that older facts are being interpreted, not reset.
133: - A legacy C5 collision without ticks is corrected by an append-forward edit
134:   and can run. With an owned ambiguous tick, runtime/source/emit refuse but
135:   fact/tick reads, inspection, verify, and export remain available.
136: - Proposed and local declarations disagree: the effective captured documents
137:   and owned ticks decide the refusal; no cache edit or concurrent declaration
138:   advance can widen the plan. A full-head CAS still protects execution.
139: - A command-only source edit with a fixed literal kind keeps an owned boundary
140:   edge only when full declaration history proves the generated identity. A
141:   template/environment source with owned ticks refuses even if unchanged today;
142:   deleting or rereading current external input never turns that refusal into
143:   inherited history.
144: 
145: The unresolved product decision is whether the explicit transition ceremony is
146: worth supporting before a future tick boundary-ID wire revision. The conservative
147: matrix above is implementable without that decision and does not narrow the
148: user's ability to reinterpret facts or inspect historical evidence.

1: # C6 independent design audit — September 6, 2026
2: 
3: Scope: source-only audit of D5/C6 continuity and compatibility. I inspected
4: Arrival capture/hydration/planning, declaration projection and diffing, source
5: template expansion, and the legacy replay/evaluation entrypoints. No
6: production or test files were changed, no live store was opened, and no Fable
7: review was run here. This note is a design gate for the requested bounded
8: implementation; it does not introduce a wire incarnation identifier.
9: 
10: ## Contract and evidence boundary
11: 
12: The current Arrival writer captures the effective declaration from bounded
13: `_decl.*` documents, then builds a detached runtime from that AST and the same
14: snapshot's facts/ticks (`libs/engine/src/engine/runtime_write.py:715-790,
15: 977-1042`). The local `.vertex` file supplies residence and ingress values;
16: `effective_declaration_from_documents` supplies the declaration semantics and
17: reattaches only those locator values (`libs/engine/src/engine/declaration.py:919-945,
18: 973-1080`). This is the correct authority split for current Arrival planning.
19: 
20: The gap is that the final effective documents erase declaration history. The
21: resolver overlays definitions and removes tombstoned subjects into a final
22: mapping (`libs/engine/src/engine/declaration.py:258-276`), while
23: `documents_to_vertex` reconstructs only the final loop map
24: (`libs/lang/src/lang/document.py:940-1035`). `diff_documents` permits a loop
25: retirement followed by a later definition of the same `(kind, subject)`; only
26: vertex identity is refused as a routine rename (`libs/lang/src/lang/document.py:1100-1159`).
27: Thus a runtime candidate receives current loop semantics plus all historical
28: facts/ticks, without knowing whether a same-named loop is an uninterrupted
29: boundary or a removed-and-recreated one.
30: 
31: Two representation limits qualify that conclusion. `materialize_vertex` always
32: installs the implicit `cite` collect loop (`libs/engine/src/engine/compiler.py:1003-1023`),
33: so tombstoning an explicit `cite` definition does not retire that runtime
34: identity; it leaves the same implicit collect identity available. A history
35: classifier must distinguish that case from actual loop retirement. Also, one
36: declaration append may be an atomic batch of several semantic documents. It
37: must evaluate effective declaration sets at the batch's committed receipt
38: boundary, rather than mistake transient partial definitions inside a batch for
39: independently observable incarnations.
40: 
41: ## Findings
42: 
43: ### 1. High: same-name removal/recreation and boundary edits reuse old consumption
44: 
45: `hydrate_snapshot` accepts a tick when `tick.origin == self._name`, looks up
46: `self._loops[tick.name]`, and invokes that current loop's `replay_boundary`
47: (`libs/engine/src/engine/vertex.py:769-849`). `plan_pending_boundaries` uses the
48: same ownership predicate and keys the latest consumed edge by `tick.name`
49: (`vertex.py:1260-1355`). Neither receives the declaration version that created
50: the tick. A loop retired in one declaration and re-added under the same name
51: therefore inherits the old tick edge/reset/count state; a boundary-kind,
52: match, count, or mode edit also applies current semantics to old edges.
53: 
54: A disposable in-memory probe confirmed the current reset interpretation: a
55: same-named historical tick leaves a rebuilt loop at `[2]` with current
56: `reset=True`, but `[1, 2]` with current `reset=False`. This is a probe of the
57: engine behavior, not a filesystem reproduction. The current DSL maps all
58: boundary forms to `reset=True` (`libs/engine/src/engine/compiler.py:541-593`),
59: while direct `Loop` construction supports carry, so the distinction still
60: matters to engine callers and future declaration vocabulary.
61: 
62: The bounded policy fork should be explicit:
63: 
64: - A normal in-place change to a loop's trigger/count/match/mode may inherit the
65:   existing edge. Current semantics then govern facts after that edge; for
66:   example, a current `after` boundary seeing an earlier owned tick is
67:   exhausted, while a current `every` boundary may continue. This is a change
68:   to future interpretation, not an automatic reset. It needs a conformance
69:   table and tests for every→after, after→every, count changes, and trigger
70:   changes.
71: - A loop removed and later re-added under the same name with an owned
72:   historical tick must refuse runtime capture/planning and ordinary edit
73:   execution. There is no role/incarnation evidence that distinguishes
74:   continuation from a new boundary. If no owned tick exists, a normal add is
75:   safe and does not imply a restart or cutoff.
76: - Fold, presentation, parse, and source-command edits with an unchanged
77:   consumption profile may continue to reinterpret facts under the effective
78:   declaration. They must not silently claim that old tick payloads were
79:   hydrated; current code re-folds facts and uses ticks only for reset/count/
80:   period bookkeeping.
81: 
82: Disabling a boundary or removing an explicit vertex citation also does not by
83: itself prove runtime retirement: the vertex name persists, and `cite` is
84: materialized implicitly. Such edits should inherit the existing vertex/loop
85: edge under the chosen in-place policy; only a proven historical role or
86: membership discontinuity should trigger refusal.
87: 
88: The minimum implementation seam is a pure classifier over declaration events
89: through H, the proposed effective declaration, and bounded ticks. It must
90: retain retirement/redefinition events before final document folding, group
91: atomic declaration batches at their committed receipt coordinate, and model
92: the implicit `cite` identity separately from explicit declaration documents.
93: Refuse only an owned same-name reappearance (and any explicitly unsupported
94: reset / carry transition); do not add an incarnation field to existing ticks.
95: 
96: ### 2. High: template and environment-generated identities lack historical proof
97: 
98: Absorbed template documents retain template/params paths, template bytes hash,
99: and params-file hash (`libs/lang/src/lang/document.py:603-634`). That can prove
100: literal template and params-file inputs were unchanged. It does not preserve
101: the resolved value of an environment-indirected parameter: `_resolve_param_indirection`
102: reads `$NAME` from today's process environment at compile time
103: (`libs/engine/src/engine/compiler.py:400-426`). `compile_sources` then uses that
104: value to instantiate the loop and, where configured, to derive its kind and
105: boundary kind (`compiler.py:429-477`). The Arrival capture path compiles this
106: current expansion after resolving historical documents
107: (`runtime_write.py:760-789`).
108: 
109: Consequently, an owned tick for a generated kind or boundary whose identity
110: comes from an unrecorded environment value cannot be associated safely with
111: its historical declaration just because today's source file and pin still
112: match. A future classifier must either find a recorded literal expansion for
113: that identity or refuse the affected runtime capture/plan. Re-reading today's
114: environment, template, or params file cannot establish past identity. This is
115: an evidence limitation, not a reason to alter the template wire format in C6.
116: 
117: The refusal cannot be limited to revisions that contain an owned tick. An
118: unresolved generated membership interval between two known revisions can hide
119: a retirement and re-add before a later owned tick, so a later current-name
120: match does not repair the continuity proof. The classifier should retain that
121: interval as unresolved and refuse the affected runtime whenever a local tick or
122: current boundary depends on it; evidence reads remain available.
123: 
124: The legacy `load_vertex_program(vars=...)` path is a separate bypass: it
125: substitutes current values in `program.py:224-267` after `load_declaration`,
126: and its reconstructed `VertexFile` omits fields including `boundary`,
127: `observers`, `lens`, and `strict`. C6 Arrival capture does not accept `vars`,
128: so this should be documented as legacy/out-of-scope or explicitly refused for
129: Arrival rather than treated as historical continuity evidence.
130: 
131: ### 3. Medium: repaired C5 collisions can leave ambiguous historical ticks
132: 
133: A tick carries `name` and `origin`, but no boundary role or declaration
134: coordinate (`libs/engine/src/engine/arrival_contract.py:209-230`). A vertex
135: boundary tick uses the vertex name (`vertex.py:934-965`); a loop tick uses the
136: loop name (`vertex.py:917-932`). C5 now refuses a *current* loop/vertex name
137: collision, but a store may already contain a tick produced before that rule.
138: After a later collision-free declaration, `hydrate_snapshot` can still see a
139: local tick with `tick.name == self._name`; it has no persisted role evidence to
140: say whether it was a vertex-level close or an old loop collision.
141: 
142: The inverse case is also unsafe: an old local-looking tick whose name is no
143: longer declared, or whose historical declaration cannot be resolved at its
144: receipt coordinate, is an unknown role. The absence of a tombstone is not
145: evidence that it is safe to attach that tick to the current loop.
146: 
147: Do not refuse every vertex-named tick: legitimate vertex-level ticks are part
148: of the supported profile. The bounded classifier should reconstruct the
149: historical declaration at the tick's receipt coordinate from the complete
150: `_decl` event stream. If that version had a same-named loop, refuse runtime
151: execution/planning for the ambiguous history; preserve facts, ticks,
152: inspection, verification, and export. If the declaration history cannot be
153: reconstructed at the tick coordinate, refuse the affected runtime path rather
154: than guess. This leaves current C5's append-forward repair available where no
155: ambiguous tick exists.
156: 
157: The evidence read must cover the complete receipt range needed by this check.
158: `TickRequest` defaults `since=0.0` (`libs/engine/src/engine/arrival_contract.py:249-255`),
159: and the Arrival writer currently calls `TickRequest()` in
160: `runtime_write.py:789,868,1014`. If negative event-time ticks are legal, that
161: default silently omits historical evidence before the Unix epoch; continuity
162: code must request an explicit lower bound (or otherwise prove the legal time
163: domain) rather than use the convenience default. This is a bounded read
164: contract issue, not a reason to reinterpret foreign/originless ticks.
165: 
166: ### 4. Medium: legacy replay/evaluation bypass Arrival origin ownership
167: 
168: Arrival hydration and pending planning correctly ignore foreign and originless
169: ticks via `_owns_tick` (`vertex.py:769-778, 805-820, 1288-1300`). The attached
170: legacy `replay` path instead sets a vertex period from
171: `store.last_tick_ts(self._name)` or the newest tick whose `name` matches,
172: without checking `origin` (`vertex.py:1135-1152`; `SqliteStore.last_tick_ts`
173: queries only `name`, `sqlite_store.py:1235-1246`). Legacy `evaluate_boundaries`
174: starts at the timestamp of the globally newest stored tick, regardless of
175: name or origin (`vertex.py:1176-1205`). A foreign/originless imported tick can
176: therefore advance the legacy cutoff or period context and suppress a local
177: boundary.
178: 
179: This is not a defect in the supported Arrival capture path, which uses
180: `hydrate_snapshot` and `plan_pending_boundaries`. It is a compatibility
181: boundary for any C6 claim covering every runtime entrypoint. Keep legacy
182: replay/evaluation unchanged in the bounded Arrival implementation unless the
183: product explicitly brings legacy semantics into scope; otherwise state that
184: origin ownership applies to Arrival hydration/planning only. Origin itself is
185: still a claim in the current tick profile: outer tick authorship is deferred,
186: so a foreign writer that can produce a valid tick with the local origin is not
187: cryptographically distinguishable by this field alone. C6 should not invent a
188: new wire role to solve that deferred profile decision.
189:

197: ## D5 — Declaration edits preserve history; reset must be explicit
198: 
199: **Recommendation:** editing a fold or its presentation appends a new
200: interpretation. It does not rewrite prior facts/ticks or automatically mint a
201: new observer, lineage, or boundary. Capture records the effective declaration
202: used for that operation; a later read may apply a later declaration and reach
203: a different conclusion honestly.
204:

206: Keep an unchanged boundary identity's established consumption edge by
207: default. A request to restart a boundary, remove and later recreate it as a

209: must be explicit. The exact restart/incarnation representation is deferred.

211: unrelated edit would then risk reopening consumed observations.

215: pass recommends the policy; it does not claim the present runtime implements
216: all of those transitions or that an existing schema can express every reset.
217: Current hydration associates historical local ticks with current loop names,
218: so remove/recreate and incompatible same-name edits can reuse an old loop's
219: boundary history. Define compatibility and historical detection before
220: promising continuity for such edits. The conservative interim direction is
221: to refuse ambiguous transitions, not to guess a reset; the predicate and

223: 
224: ## D6 — Result identity describes evidence and actions separately
225:

241: maintainer invocation or a post-write check. Unknown derived effects remain

244: discard the cause.

699: def vertex_to_documents(ast: VertexFile) -> list[Document]:
700:     """Decompose a ``VertexFile`` AST into per-subject declaration documents.
701: 
702:     Emission order (deterministic): the ``_decl.vertex-defined`` singleton,
703:     then ``_decl.kind-defined`` per loop, ``_decl.observer-defined`` per
704:     observer, ``_decl.member-defined`` per combine entry, ``_decl.source-defined``
705:     per source (bare/template entries first, then inline sources per block),
706:     and ``_decl.lens-defined`` if a lens is declared.
707: 
708:     Each multi-instance document carries an ``order`` field (encounter
709:     position) and a subject deduplicated per kind (see module docstring:
710:     "Order is meaning", "Subject uniqueness"). Residence (``store`` locator,
711:     ``path``) is excluded. Every payload is validated JSON-safe before return.
712:     """
713:     docs: list[Document] = []
714:     order = 0  # global encounter position across all multi-instance documents
715: 
716:     # Per-kind subject deduplication. Allocate against the SET of subjects
717:     # already issued for this kind (not a per-base counter) so a suffix never
718:     # lands on a naturally-occurring subject: bases ["base", "base", "base#2"]
719:     # → ["base", "base#2", "base#3"], all distinct. Identity only — projection
720:     # reconstructs every value from the payload, never from the subject.
721:     issued: dict[str, set[str]] = {}
722: 
723:     def _subject(kind: str, base: str) -> str:
724:         seen = issued.setdefault(kind, set())
725:         candidate = base
726:         n = 1
727:         while candidate in seen:
728:             n += 1
729:             candidate = f"{base}#{n}"
730:         seen.add(candidate)
731:         return candidate
732: 
733:     def _emit(kind: str, base: str, payload: dict[str, Any]) -> None:
734:         nonlocal order
735:         payload["order"] = order
736:         order += 1
737:         docs.append(Document(kind=kind, subject=_subject(kind, base), payload=payload))
738: 
739:     # vertex-defined singleton — subject is the vertex name (self); no order.
740:     docs.append(
741:         Document(
742:             kind=DECL_VERTEX_DEFINED,
743:             subject=ast.name,
744:             payload={
745:                 "name": ast.name,
746:                 "strict": ast.strict,
747:                 "observer_scoped": ast.observer_scoped,
748:                 "discover": ast.discover,
749:                 "emit": ast.emit,
750:                 "routes": dict(ast.routes) if ast.routes is not None else None,
751:                 "vertices": [str(p) for p in ast.vertices]
752:                 if ast.vertices is not None
753:                 else None,
754:                 "boundary": [_boundary_to_json(b) for b in ast.boundary],
755:                 # sources live in their own documents; this flag preserves the
756:                 # None-vs-empty-tuple distinction of VertexFile.sources.
757:                 "sources_present": ast.sources is not None,
758:                 # authoritative block structure (index + mode); None when there
759:                 # are no sources_blocks. Members are the inline source docs.
760:                 "source_blocks": [

1040: # Subject-granular diff — the edit ceremony's grammar half (SPEC §9.2, S4)
1041: # ===========================================================================
1042: #
1043: # Re-absorbing an edited ``.vertex`` diffs its freshly-parsed document set
1044: # against the store's fold head (Latest per (kind, subject), self-lineage) and
1045: # re-emits ONLY the changed subjects as whole documents. This module supplies
1100: def diff_documents(head: Any, new: Any) -> list[Change]:
1101:     """Diff a fold head against a freshly-parsed document set → changes.
1102: 
1103:     ``head`` and ``new`` are each an iterable of documents — :class:`Document`
1104:     namedtuples or plain ``{"kind", "subject", "payload"}`` mappings (the
1105:     resolver returns the latter). Both are keyed by ``(kind, subject)``.
1106: 
1107:     Yields (in a deterministic order — additions/modifications in ``new``'s
1108:     iteration order, then removals in ``head``'s iteration order):
1109: 
1110:     - ``"added"`` — a ``(kind, subject)`` in ``new`` but not ``head``.
1111:     - ``"modified"`` — present in both, payloads differ by value.
1112:     - ``"removed"`` — in ``head`` but not ``new``; emitted as the paired
1113:       tombstone kind.
1114: 
1115:     Raises :class:`EditRefused` if a removal targets a singleton with no
1116:     tombstone (``_decl.lens-defined`` → vocabulary gap; ``_decl.vertex-defined``
1117:     → identity/rename). Unchanged subjects yield nothing.
1118:     """
1119:     head_map: dict[tuple[str, str], dict[str, Any]] = {}
1120:     for item in head:
1121:         k, s, p = _as_triple(item)
1122:         head_map[(k, s)] = p
1123: 
1124:     new_map: dict[tuple[str, str], dict[str, Any]] = {}
1125:     changes: list[Change] = []
1126:     for item in new:
1127:         k, s, p = _as_triple(item)
1128:         new_map[(k, s)] = p
1129:         prev = head_map.get((k, s))
1130:         if prev is None:
1131:             changes.append(Change(kind=k, subject=s, payload=p, annotation="added"))
1132:         elif prev != p:
1133:             changes.append(Change(kind=k, subject=s, payload=p, annotation="modified"))
1134:         # else unchanged → nothing
1135: 
1136:     for (k, s), _p in head_map.items():
1137:         if (k, s) in new_map:
1138:             continue
1139:         tombstone = DEFINED_TO_TOMBSTONE.get(k)
1140:         if tombstone is None:
1141:             if k == DECL_VERTEX_DEFINED:
1142:                 raise EditRefused(
1143:                     f"vertex identity change: the vertex-defined subject "
1144:                     f"{s!r} was removed (a rename). The vertex name is "
1145:                     "meaning-critical identity — a post-genesis rename is a "
1146:                     "deliberate ceremony, not an edit; not supported by "
1147:                     "re-absorb."
1148:                 )
1149:             raise EditRefused(
1150:                 f"cannot remove singleton {k!r} (subject {s!r}): the frozen "
1151:                 "declaration vocabulary has no tombstone for it "
1152:                 "(SPEC §9.2 — a lens is replaced by re-definition, never "
1153:                 "removed). Re-add the lens, or edit it in place; removal is a "
1154:                 "pending coordinated vocabulary change "
1155:                 "(thread:decl-lens-tombstone-vocab-gap)."
1156:             )
1157:         changes.append(Change(kind=tombstone, subject=s, payload=None, annotation="removed"))
1158: 
1159:     return changes
