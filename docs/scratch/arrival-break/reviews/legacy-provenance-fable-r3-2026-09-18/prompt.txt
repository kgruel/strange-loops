1: # Loops live Arrival cutover plan
2: 
3: This is an execution plan for a future, separately authorized maintenance
4: window. It does not authorize a live migration, key access, descriptor swap or
5: write. It uses the user-approved `legacy-unattributed-v1` transformation and
6: the fresh runtime epoch; it does not recast the old tick-window commitments as
7: unchanged commitments over the prepared archive.
8: 
9: The September 18 copy rehearsal is evidence for the path, not an input to this
10: cutover. Its source snapshot, prepared copy, lineage, report and credentials
11: are never promoted to production. The live window starts with a new snapshot
12: and independently captured pins.

14: ## Supported runtime boundary
15: 
16: Use the descriptor-first SDK after the descriptor is published:
17: 
18: - Reads and inspection: `inspect_declaration`, `read_summary`, `read_facts`,
19:   `read_ticks`, `read_state`, `read_timeline`, `search_facts`, `sync_target`,

21: - Writes: `preview_emission`, `emit_fact`, `emit_batch`,

27: - Preservation: `export_target` creates an exclusive exact Arrival export at a
28:   captured head.

30:   only `recover_arrival_adoption(intent_path)` may reconcile it. Recovery has
31:   no signer or epoch argument.

34: `loops store`, `loops store absorb`, `loops store adopt`, `loops store reanchor`,
35: or `loops store reindex` against the candidate or live descriptor. Those
36: commands retain the legacy SQLite/canonical-store and `open_vertex` consumer
37: paths. This plan has not established a refusal for each command, including
38: `loops store absorb`; it makes no safety claim based on such a refusal. Keeping
39: them disabled is the protection. They do not form a reviewed Arrival-v2 writer

256: ## Publication and writer handoff
257: 
258: There are two distinct publication points:
259: 
260: 1. Migration and adoption make durable records in `ARRIVAL_STORE`, while only
261:    `CANDIDATE_VERTEX` names them. This is pre-live evidence and does not change
262:    `LIVE_VERTEX`.
263: 2. The final descriptor replacement makes the candidate declaration live. It
264:    must be an atomic same-directory replace that first confirms the live vertex
265:    still equals the pinned original bytes and then fsyncs the directory. Save
266:    a separately named prepublication backup under `ARCHIVE_ORIGINAL` (for
267:    example `project.vertex.prepublish`); do not overwrite it on a retry.
268: 
269: Prepare the final replacement file in `LIVE_VERTEX.parent` so the final
270: `os.replace` is same-directory. Under the already-held quiescence lock, a small
271: one-shot publication procedure must do the following in order:
272: 
273: 1. Read `LIVE_VERTEX` and `CANDIDATE_VERTEX`; require their SHA-256 values to
274:    equal the recorded original and candidate pins. Re-parse the candidate and
275:    require its descriptor to name the final absolute `ARRIVAL_STORE`, the
276:    pinned lineage, and authority role.
277: 2. Create and `fsync` the separately named prepublication backup exclusively,
278:    or, on a retry, require its existing hash to equal the original pin. Then
279:    create `LIVE_VERTEX.parent / ".<name>.arrival-cutover"` exclusively with
280:    the candidate bytes, `fsync` it, reread/hash it, and require the candidate
281:    hash again. An existing stage path refuses.
282: 3. Reread and hash `LIVE_VERTEX` one final time. If it no longer equals the
283:    original pin, remove only the uninstalled stage file and refuse.
284: 4. Call `os.replace(stage_path, LIVE_VERTEX)`, then open and `fsync` the parent
285:    directory. Reread/hash the new live vertex and require the candidate pin.
286: 
287: This is an atomic same-directory replacement under quiescence; it is not an
288: atomic compare-and-swap. Quiescence is the guarantee against a concurrent
289: editor; the two live-byte checks detect drift observed before replacement. The
290: procedure's receipt binds the old and candidate hashes, A, stable Arrival path,
291: backup hash, and replacement result.
292: 
293: ```python
294: def publish_vertex(live: Path, candidate: Path, backup: Path) -> tuple[str, str]:
295:     old = live.read_bytes()
296:     replacement = candidate.read_bytes()
297:     old_hash = hashlib.sha256(old).hexdigest()
298:     replacement_hash = hashlib.sha256(replacement).hexdigest()
299:     if old_hash != ORIGINAL_VERTEX_SHA256 or replacement_hash != CANDIDATE_VERTEX_SHA256:
300:         raise RuntimeError("cutover input hash changed")
301:     stage = live.parent / f".{live.name}.arrival-cutover"
302:     if backup.exists():
303:         if hashlib.sha256(backup.read_bytes()).hexdigest() != old_hash:
304:             raise RuntimeError("existing prepublication backup hash mismatch")
305:     else:
306:         _write_exclusive_and_fsync(backup, old)
307:     if hashlib.sha256(backup.read_bytes()).hexdigest() != old_hash:
308:         raise RuntimeError("original backup hash mismatch")
309:     if stage.exists():
310:         raise RuntimeError("exclusive live-directory stage already exists")
311:     _write_exclusive_and_fsync(stage, replacement)
312:     if hashlib.sha256(stage.read_bytes()).hexdigest() != replacement_hash:
313:         raise RuntimeError("staged candidate changed")
314:     if live.read_bytes() != old:  # quiescence check immediately before replace
315:         stage.unlink(missing_ok=True)
316:         raise RuntimeError("live vertex changed during publication")
317:     os.replace(stage, live)
318:     _fsync_directory(live.parent)
319:     if hashlib.sha256(live.read_bytes()).hexdigest() != replacement_hash:
320:         raise RuntimeError("published vertex hash mismatch")
321:     return old_hash, replacement_hash
322: ```
323: 
324: This is illustrative algorithm text, not an implemented cutover command.
325: `_write_exclusive_and_fsync` opens with exclusive creation, writes, flushes and
326: calls `os.fsync`; `_fsync_directory` opens the directory read-only and calls
327: `os.fsync`. Before use, the cutover transcript must add the step-1 descriptor
328: reparse and receipt serialization, then record a disposable-directory rehearsal
329: of the exact fragment.
330: 
331: Keep writers stopped through the replacement, reopen the descriptor only with
332: the SDK operations above, and repeat `verify_target`, `sync_target`,
333: `inspect_declaration`, `read_summary`, and `read_state` against `LIVE_VERTEX`.
334: Run `preview_emission` for the separately approved first business payload with
335: the production mapped provider against `LIVE_VERTEX`; require
336: `read_path == "arrival"` and `captured_head == A`, with no append. Record the
337: explicit `CUTOVER_BINDINGS` and `CUTOVER_STATE` paths used by that process and
338: confirm no binding or head-journal material was resolved from the candidate or
339: from a default-state root.
340: Only then hand each inventoried writer to a descriptor-first SDK integration:
341: 
342: - interactive/API fact writer: `preview_emission` then `emit_fact` with the
343:   production mapped provider;
344: - batch ingest: `emit_batch` with the same mapped provider and captured
345:   result/commit evidence;
346: - declaration management: `edit_declaration` and its recovery API;
347: - source/cadence jobs: `run_sources` with the production collector factory,
348:   dispatcher, observer, mapped provider, and `CUTOVER_STATE` environment;
349: - CLI-only workflows: remain disabled until they have a reviewed adapter to
350:   those descriptor-first SDK calls.
351: 
352: The handoff receipt names every enabled writer and its SDK version, plus how
353: each excluded legacy command or scheduled job was disabled. No legacy or raw
354: JSONL/SQLite writer is re-enabled.
355: 
356: ## Failure disposition and rollback
357: 
358: Before final descriptor replacement, any failed migration, provenance, report,
359: adoption, projection or read gate leaves `LIVE_VERTEX` and `LIVE_SOURCE`
360: unchanged. Preserve the candidate Arrival file, report, intent and receipts as
361: evidence; do not truncate, delete, reuse, or append a second anchor. Resume is
362: allowed only through the documented migration/adoption recovery paths when
363: their exact input pins still hold.
364: 
365: After descriptor replacement but before any post-A business write, legacy
366: routing may be restored only when all of the following are recorded while
367: writers and source jobs are stopped:
368: 
369: - `verify_target(LIVE_VERTEX)` captures a head exactly equal to A in lineage,
370:   ordinal, and record hash; the Arrival file SHA-256 equals the recorded
371:   post-adoption A pin.
372: - `LIVE_VERTEX` SHA-256 equals the candidate pin, and `LIVE_SOURCE` SHA-256
373:   still equals its original snapshot pin.
374: - The exclusive same-directory restore stage is written from the separately
375:   named prepublication backup, fsynced and rehashed against the original vertex
376:   pin before `os.replace`; after replace, fsync the directory and require the
377:   live vertex hash to equal that original pin.
378: 
379: If any condition fails, restoration is forbidden and disposition is forward
380: only. When it succeeds, retain the candidate Arrival lineage and adoption
381: anchor; this is a service-routing reversal, never a history deletion.
382: 
383: After the first post-A write, do not restore the legacy vertex as a writable
384: fallback. It would conceal new authoritative facts. Stop writers, retain the
385: Arrival descriptor, head journal, mapped-binding root, original archive and
386: exact export, then recover or correct forward on the Arrival lineage. If
387: service must be limited during that work, use descriptor-first read-only SDK
388: access at the recorded head; do not drop or replay new facts into the legacy
389: source.
390: 
391: ## Remaining blockers and decisions
392: 
393: 1. The provenance verifier command above is under development. Its reviewed
394:    implementation and a fresh-copy passing receipt are required.
395: 2. The illustrative same-directory publication algorithm needs its descriptor
396:    reparse, receipt serialization, and disposable-directory rehearsal completed
397:    before use. The existing migration publisher cannot replace a distinct live
398:    vertex.
399: 3. Every production writer must either have a descriptor-first SDK handoff or
400:    remain disabled. `run_sources` is available for source jobs, but the current
401:    CLI emit/sync/source workflows have no supported Arrival-v2 adapter today.
402:    Refusal behavior for legacy CLI commands, including `store absorb`, is
403:    unverified; disablement is the safety gate, not an assumed refusal.
404: 4. The maintenance owner must complete the real writer inventory and obtain a

406:    rather than a policy choice.
407:

410: boundaries with audited transformation, and no legacy writable fallback after
411: an Arrival write. The four items above are integration gates, not decisions to
412: defer to the cutover window.
