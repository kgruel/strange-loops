1: # A fresh Loops store for Atlas observations
2: 
3: This walkthrough uses `loops-min` to capture Atlas's photograph architecture
4: and keep evolving notes about it. You will create a credential binding and a
5: fresh Arrival store, declare two folds, append observations, and compare folded
6: state with the complete observation history.
7: 
8: The input is `~/Code/gruel.network/docs/atlas/architecture.json`, generated by
9: that project's architecture tooling. It describes **configured architecture**.
10: It includes source selectors and explicit unknowns; it does not establish live
11: health. This walkthrough reads that file and writes a separate scratch store.
12: It does not connect the Atlas browser to Loops or migrate an existing store.
13: 
14: The commands use the `arrival/finish` implementation at checkpoint `d4e5792d`.
15: Prerequisites: Python 3.11+, `uv`, and the two local checkouts. Run the Bash
16: blocks below, in order, in **one Bash session**. Later steps use variables and
17: functions established by earlier steps. Start a fresh scratch directory for
18: each run rather than repeating writes into an earlier run.
19: 
20: ## 1. Prepare an isolated workspace
21: 
22: Adjust `LOOPS_CHECKOUT` if your Arrival checkout is elsewhere. The virtual
23: environment, credentials, witness state, projections, and command receipts all
24: live under `ATLAS_WORK`. Its path is printed so you can inspect it afterward.
25: 
26: ```bash
27: set -euo pipefail
28: umask 077
29: export LOOPS_CHECKOUT="$HOME/Code/loops-wt/arrival-finish"
30: cd "$HOME/Code/gruel.network/docs/atlas"
31: test -f architecture.json
32: export ATLAS_WORK="$(mktemp -d "${TMPDIR:-/tmp}/atlas-loops.XXXXXX")"
33: export UV_PROJECT_ENVIRONMENT="$ATLAS_WORK/venv"
34: export XDG_STATE_HOME="$ATLAS_WORK/state"
35: export XDG_CONFIG_HOME="$ATLAS_WORK/config"
36: export LOOPS_HOME="$ATLAS_WORK/loops-config"
37: export ATLAS_KEYS="$ATLAS_WORK/credentials"
38: export ATLAS_VERTEX="$ATLAS_WORK/atlas.vertex"
39: 
40: uv sync --project "$LOOPS_CHECKOUT" --package loops-min --no-dev
41: export LOOPS_MIN="$UV_PROJECT_ENVIRONMENT/bin/loops-min"
42: cp architecture.json "$ATLAS_WORK/architecture.json"
43: printf 'Workspace: %s\n' "$ATLAS_WORK"
44: ```
45: 
46: Use `loops-min`, the new JSON CLI. The legacy `loops` executable is a different
47: application. Each successful command below returns an envelope with `ok: true`
48: and an SDK-owned `result`; saved JSON files retain that evidence.
49: 
50: ## 2. Choose an observer and initialize
51: 
52: `atlas-guide` is the observer authoring these example observations.
53: `atlas-demo` is the namespace for its **local credential binding**.
54: `atlas-notes` is the vertex's name. These names serve different purposes; none
55: is inferred from `atlas.vertex`.
56: 
57: The binding token identifies this credential-creation operation. Creating a
58: binding alone does not authorize its observer in a store. Initialization uses
59: the binding to sign the new store's founding records and declaration.
60: 
61: ```bash
62: "$LOOPS_MIN" credential-create "$ATLAS_KEYS" \
63:   --namespace atlas-demo --observer atlas-guide --token atlas-guide-key-v1 \
64:   > "$ATLAS_WORK/binding.json"
65: 
66: atlas_write() {
67:   "$LOOPS_MIN" "$@" \
68:     --credential-root "$ATLAS_KEYS" \
69:     --credential-namespace atlas-demo --receipt-observer atlas-guide
70: }
71: 
72: atlas_write init "$ATLAS_VERTEX" --name atlas-notes \
73:   --location "$ATLAS_WORK/atlas.arrival" --observer atlas-guide --strict \
74:   > "$ATLAS_WORK/init.json"
75: "$LOOPS_MIN" inspect "$ATLAS_VERTEX" > "$ATLAS_WORK/inspect-initial.json"
76: ```
77: 
78: Fresh initialization creates and synchronizes the declaration history. There
79: is no separate adoption step. The initial scaffold contains an `item` kind;
80: the next step replaces that unused example with the kinds we want.
81: 
82: ## 3. Declare what the observations mean
83: 
84: We will keep one latest **whole graph** per scope in `atlas.snapshot`, and one
85: latest note per subject in `atlas.note`. A whole snapshot keeps source indices,
86: relationships, unknowns, and revision together; source index `16` in one
87: snapshot must not be interpreted using another snapshot's source list.
88: 
89: The `"by"` fold replaces the value for a matching payload key in folded state.
90: It does not replace old facts. Selection follows receipt order, not the largest
91: authored timestamp. With several observers, this particular note fold would
92: choose the last received note across them; use a different grouping or vertex
93: definition if you want their interpretations kept separately.
94: 
95: Create a proposal from the freshly generated scaffold, retaining its residence
96: and observer block. Apply it through the CLI so the declaration change is
97: recorded in the store.
98: 
99: ```bash
100: python3 - <<'PY'
101: import os
102: from pathlib import Path
103: 
104: work = Path(os.environ["ATLAS_WORK"])
105: text = Path(os.environ["ATLAS_VERTEX"]).read_text()
106: prefix, _ = text.split("\nloops {", 1)  # This walkthrough's fresh scaffold only.
107: proposal = prefix + '''
108: loops {
109:   atlas.snapshot {
110:     fold { snapshots "by" "scope" }
111:   }
112:   atlas.note {
113:     fold { notes "by" "subject" }
114:   }
115: }
116: '''
117: (work / "proposed.vertex").write_text(proposal)
118: PY
119: 
120: atlas_write declaration "$ATLAS_VERTEX" \
121:   --proposed-file "$ATLAS_WORK/proposed.vertex" --observer atlas-guide \
122:   > "$ATLAS_WORK/declaration.json"
123: ```

125: ## 4. Append the graph and a first note together
126: 
127: The batch below retains the copied graph, its revision, and a hash of the
128: exact input bytes. The note references that snapshot's fact ID and the photo
129: mount entity. Those payload references are application data, not automatic
130: foreign-key validation. The message preserves the graph's unresolved backing
131: claim; it does not infer a disk or network filesystem from a host path.
132: 
133: ```bash
134: python3 - <<'PY'
135: import hashlib
136: import json
137: import os
138: from pathlib import Path
139:

141: raw = (work / "architecture.json").read_bytes()
142: graph = json.loads(raw)
143: assert graph["schema_version"] == 1
144: assert graph["scope"] == "photographs" and graph["state"] == "configured"
145: unknown = next(u for u in graph["unknowns"]
146:                if u["subject"] == "mount:immich-photos" and u["field"] == "backing")
147: snapshot_id = "atlas-snapshot-" + graph["revision"]

149:     "subject": unknown["subject"], "snapshot_fact_id": snapshot_id,
150:     "status": "question", "message": unknown["reason"],
151: }
152: batch = [
153:     {"id": snapshot_id, "kind": "atlas.snapshot", "observer": "atlas-guide",
154:      "origin": "docs/atlas/architecture.json",
155:      "payload": {"scope": graph["scope"], "graph": graph,
156:                  "input_sha256": hashlib.sha256(raw).hexdigest()}},
157:     {"id": "atlas-note-1", "kind": "atlas.note", "observer": "atlas-guide",
158:      "origin": "atlas-greenfield-guide", "payload": note},
159: ]
160: (work / "batch.json").write_text(json.dumps(batch))
161: note.update(status="follow-up",
162:             message="Inspect the family VM filesystem and mount source before naming the backing.")
163: (work / "follow-up.json").write_text(json.dumps(note))
164: PY

166: atlas_write emit-batch "$ATLAS_VERTEX" \
167:   --facts-json "$(cat "$ATLAS_WORK/batch.json")" > "$ATLAS_WORK/batch-receipt.json"
168: "$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.note \
169:   > "$ATLAS_WORK/notes-before.json"
170: ```
171: 
172: The example is a small batch passed as a command argument. A large estate or
173: continuous importer needs an SDK-based ingestion path; this CLI does not yet
174: provide a source runner or streaming import command.
175: 
176: ## 5. Append a follow-up and compare views
177: 
178: The follow-up is an example of an observer's intended investigation. It makes
179: no new claim about actual storage backing. It uses a new fact ID and the same
180: subject, so the note fold advances while both notes remain available.
181: 
182: ```bash
183: atlas_write emit "$ATLAS_VERTEX" atlas.note --observer atlas-guide \
184:   --origin atlas-greenfield-guide --id atlas-note-2 \
185:   --payload-json "$(cat "$ATLAS_WORK/follow-up.json")" \
186:   > "$ATLAS_WORK/follow-up-receipt.json"
187: 
188: "$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.note \
189:   > "$ATLAS_WORK/notes-after.json"
190: "$LOOPS_MIN" state "$ATLAS_VERTEX" --kind atlas.snapshot \
191:   > "$ATLAS_WORK/snapshot-state.json"
192: "$LOOPS_MIN" facts "$ATLAS_VERTEX" --kind atlas.note --order oldest --limit 10 \
193:   > "$ATLAS_WORK/note-history.json"
194: 
195: python3 - <<'PY'
196: import json
197: import os
198: from pathlib import Path
199: 
200: work = Path(os.environ["ATLAS_WORK"])
201: def result(name):
202:     envelope = json.loads((work / name).read_text())
203:     assert envelope["ok"] is True
204:     return envelope["result"]
205: 
206: subject = "mount:immich-photos"
207: before = result("notes-before.json")["sections"]["atlas.note"]["notes"][subject]
208: after = result("notes-after.json")["sections"]["atlas.note"]["notes"][subject]
209: history = result("note-history.json")
210: assert before["status"] == "question" and after["status"] == "follow-up"
211: assert history["truncated"] is False
212: assert [fact["id"] for fact in history["items"]] == ["atlas-note-1", "atlas-note-2"]

216: print("History:", len(history["items"]), "notes; captured graph preserved intact")

218: ```
219: 
220: `state` is the interpretation chosen by the declaration. `facts` is the
221: underlying history. Here, changing what you see required appending an
222: observation; the earlier observation and captured configuration remain intact.
223: 
224: ## 6. Inspect, verify, and capture the prefix
225: 
226: Ordinary successful writers synchronize their projection. `sync` below checks
227: that boundary explicitly; inspect its actual result instead of assuming that
228: every successful append necessarily completed all later work.
229: 
230: ```bash
231: "$LOOPS_MIN" inspect "$ATLAS_VERTEX" > "$ATLAS_WORK/inspect-final.json"
232: "$LOOPS_MIN" verify "$ATLAS_VERTEX" > "$ATLAS_WORK/verify.json"
233: "$LOOPS_MIN" sync "$ATLAS_VERTEX" > "$ATLAS_WORK/sync.json"
234: "$LOOPS_MIN" export "$ATLAS_VERTEX" "$ATLAS_WORK/captured.jsonl" \
235:   > "$ATLAS_WORK/export.json"
236: printf 'Receipts, declaration, store, and captured prefix: %s\n' "$ATLAS_WORK"
237: ```
238: 
239: `inspect` compares the local declaration with effective declaration history. `verify`
240: reports grammar, density, lineage, and hash-chain claims; it does not establish
241: signature authorship, external key trust, or projection agreement. `sync`
242: reports the captured and projected heads. Result fields vary by operation:
243: `emit` supplies `signed`, `witnessed`, and `commit`; `emit-batch` supplies a
244: shared commit and witness status plus each item's signing status. Initialization
245: reports a head and phase, while declaration editing reports its commit,
246: resulting head, and phase. Selecting mapped credentials alone is not a universal
247: mandatory-signing policy.
248: 
249: The export is a captured wire prefix at a new pathname. It is not a standalone
250: backup of credentials, local witnesses, and descriptor, and the CLI does not
251: yet provide empty-receiver import. Keep this scratch workspace if you want to
252: inspect or continue it; a durable project store should use deliberate stable
253: locations and a planned credential/witness backup policy.
254: 
255: ## If a command is interrupted
256: 
257: The guide stops on a nonzero exit. Retain stdout JSON, stderr, the binding
258: token, and any returned intent/commit evidence. Exit 6 means ledger custody
259: committed or may have committed, or a credential mutation is incomplete. Do not
260: blindly repeat the operation. Stable fact
261: IDs help identify the operation but are not a blanket retry guarantee.
262: 
263: Recovery commands, when the corresponding retained intent warrants them:
264: 
265: ```text
266: loops-min credential-recover ROOT --namespace atlas-demo --observer atlas-guide --token atlas-guide-key-v1
267: loops-min init-recover TARGET
268: loops-min declaration-recover INTENT
269: ```
270: 
271: Recovery uses the reserved operation's evidence. It does not choose a new
272: observer, lineage, or signatures. Successful initialization removes its intent;
273: running `init-recover` after normal success is not a health check.
274:

===== apps/loops-min/README.md =====
1: # loops-min
2: 
3: `loops-min` is the transitional JSON process client for the headless `sdk`
4: package. It provides descriptor/read operations, verification, projection and
5: search maintenance, exact export, explicit restore-forward, and a mapped-only
6: Arrival writer surface. Empty-receiver import, admission, a generic replicate
7: command, and legacy writer retirement remain later work.
8: 
9: Writer commands require all of `--credential-root`, `--credential-namespace`,
10: and `--receipt-observer`. They never select locator-derived credentials or fall
11: back to a legacy writer or create keys implicitly. The founding binding must be
12: pre-provisioned for `init`; pre-provision every author and receipt binding used
13: by a signed workflow. Selecting the mapped provider does not make every domain
14: mandatory: an absent optional signer retains the SDK's unsigned behavior under
15: the captured declaration and signed-era rules. Callers should inspect each
16: result's `signed` and `witnessed` evidence.
17: 
18: Credential mutations are explicit SDK-backed commands. Their tokens name one
19: durable operation and should be retained with the JSON result or error:
20: 
21: ```text
22: loops-min credential-create /keys --namespace tenant --observer alice \
23:   --token setup-alice
24: loops-min credential-recover /keys --namespace tenant --observer alice \
25:   --token setup-alice
26: loops-min credential-bind-existing-ref /keys --namespace tenant \
27:   --observer bob --token bind-bob --key-ref KEY_REF \
28:   --expected-public-key PUBLIC_KEY
29: loops-min credential-import-legacy /keys --namespace tenant --observer carol \
30:   --token import-carol --vertex old.vertex
31: ```
32: 
33: `credential-recover` uses the exact namespace, observer, and token of a retained
34: binding intent. An incomplete result is a reconciliation boundary, not an
35: automatic retry instruction. Existing-reference binding and legacy import are
36: explicit selections; the client does not search for keys or serialize custody
37: implementation objects.
38: 
39: `init` always requests an Arrival file target and never uses `init_vertex`'s
40: legacy default. A minimal lifecycle is:
41: 
42: ```text
43: loops-min init app.vertex --name app --location /data/app.arrival \
44:   --observer alice --credential-root /keys --credential-namespace tenant \
45:   --receipt-observer alice --strict
46: loops-min emit app.vertex item --payload-json '{"value":1}' --observer alice \
47:   --credential-root /keys --credential-namespace tenant --receipt-observer alice
48: loops-min emit-batch app.vertex --facts-json '[{"kind":"item","payload":{"value":2},"observer":"alice","id":"item-2"}]' \
49:   --credential-root /keys --credential-namespace tenant --receipt-observer alice
50: ```
51: 
52: `emit` requires a JSON object payload. `emit-batch` requires an array of JSON
53: objects and passes their observer, ID, timestamp, origin, and admission fields
54: to the SDK, retaining its existing defaults and coercion rules. Transport JSON rejects duplicate keys and non-finite
55: numbers before credential resolution. The client does not retry unknown
56: outcomes; stable IDs and the SDK's returned evidence are the reconciliation
57: boundary.
58: 
59: `declaration target.vertex --proposed-file next.vertex --observer alice ...`
60: passes the file's text to the SDK's captured declaration-edit protocol. If an
61: edit reports an intent after a durable interruption,
62: `declaration-recover INTENT` resumes it without resolving credentials again.
63: Likewise, `init-recover TARGET` uses only the target's reserved initialization
64: intent. It does not accept credentials, observer, backend, location, name, or
65: strictness overrides. It does not choose a new lineage or re-sign the reserved
66: bootstrap records.
67: 
68: `loops-min export target.vertex captured.jsonl` publishes a complete captured
69: wire prefix at a new pathname and returns the SDK manifest in its JSON result.
70: It never replaces an existing output. Export publication failures report
71: whether the complete artifact became visible before directory durability failed.
72: 
73: `loops-min restore-forward source.vertex receiver.vertex` restores an existing
74: exact copy through the witnessed source head. It preserves the receiver's
75: role and reports its before/after heads and commit receipt. Ordinary opens
76: continue to refuse older copies. Unknown or incomplete outcomes retain the
77: identity evidence needed to reconcile custody before repeating the operation.
78: 
79: Each successful invocation prints one `{"ok": true, "result": ...}` JSON
80: object. Failures print one JSON error object on stdout and a concise diagnostic
81: on stderr. Result objects are serialized with the SDK model's `as_dict()`;
82: continuation capabilities remain process-local and are reported without a
83: fake cursor token.
84: 
85: Exit status 2 covers argument, transport JSON, local input-file, and SDK
86: invalid-input/configuration errors (including missing founding credentials); 3
87: means a recognized unsupported operation or target; 4 is a target, custody,
88: projection, publication, or contract refusal/outcome; 5 is admission or
89: ceremony refusal; and 6 means ledger custody committed or may have committed,
90: or a credential-binding mutation is incomplete. Status
91: 4 does not by itself prove zero derived or publication effects. Status 6 is
92: not permission to retry: the JSON error retains commit, IDs, intent, and
93: outcome evidence supplied by the SDK. A credential-binding incomplete result
94: has a binding token and phase rather than a ledger Commit or fact IDs; an
95: unknown phase does not prove that a durable binding intent exists.
96: 
97: The executable is deliberately named `loops-min` while the legacy `loops`
98: application remains in the workspace. It has no presentation, storage, or
99: legacy CLI dependency.
100: 
101: For a complete fresh-store example with tested commands, see
102: [A fresh Loops store for Atlas observations](../../docs/guides/atlas-greenfield-cli.md).
103: 
104: The global `--pretty` option may appear before or after a command. Argument
105: errors also use the JSON envelope and exit with status 2. A built-wheel smoke
106: can be run from a clean environment by building `loops-min`, installing it
107: alongside the local SDK dependency wheels, and invoking `loops-min --help` and
108: one temporary Arrival `summary`; the package does not require a repository
109: checkout at runtime.
