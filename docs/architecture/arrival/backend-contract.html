Specification 03 · storage implementations

Arrival Backend Contract

The minimum guarantees a file, embedded database, SQL server, or remote service must provide before it may hold a lineage’s authoritative append head.

Draft v1 Storage-neutral authority 26 August 2026
01

Purpose and conformance profiles

The backend contract turns the Arrival Protocol into a replaceable implementation boundary. It is intentionally stricter for a backend that assigns ordinals than for an archive that merely preserves bytes.

ProfileMay assign new ordinals?Required capabilities
AuthorityYes, when designatedMint, full-head CAS append, durable atomic records (and groups to its declared limit), consistent scan, verify, canonical export
ReplicaNoExact-next replication, prefix verification, deterministic scan and export
ArchiveNoImmutable prefix bundle, manifest and digest verification
QueryNo ledger authorityProjection watermark, deterministic row expansion, rebuild or direct ledger query

Profiles compose. A DuckDB adapter may implement Authority and Query. A PostgreSQL service may implement Authority, Replica, and Query. A compressed object-store bundle may implement only Archive. A weak store is still useful; it simply cannot advertise guarantees it does not have.

Authority is a role, not a species

Supporting the Authority profile does not make every instance authoritative. The store descriptor and control plane designate one instance for one lineage; all other copies remain replicas until an explicit transfer.

02

Explicit store descriptors

Backend selection MUST be explicit. Implementations must not infer authority, canonical format, or migration behavior from .arrival, .duckdb, .db, or another suffix. A descriptor resolves the logical store to an adapter and location.

Illustrative descriptorYAML shape, not yet a ratified file format
arrival:
  protocol: 1
  backend: duckdb
  location: ./personal.duckdb
  lineage: 01ARZ3NDEKTSV4RRFFQ69G5FAV
  role: authority
  query: direct
  witness: keychain://loops/arrival/personal

Descriptor requirements

  • backend selects a registered adapter; it is never guessed.
  • location is interpreted only by that adapter and may be a path, DSN reference, or service URL.
  • lineage, when already known, is checked against genesis rather than trusted as a replacement for it.
  • role expresses operator intent; the backend still verifies that it can safely perform the requested operation.
  • Secrets and raw credentials SHOULD be referenced from a secret provider, not embedded in the descriptor.
  • Descriptors that can mutate an authority require stronger filesystem or control-plane protection than ordinary read addresses.
Ruled — descriptor residence

Locally the descriptor dissolves into the .vertex store clause, which was already the explicit declaration — nothing is sniffed from disk. A standalone descriptor artifact earns its place only at the service boundary; local cutover atomicity is an atomic replace of the declaring file (decision:design/arrival-suite-review-dispositions §4).

No path-shaped privilege escalation

Opening an exported .arrival path does not grant it authority merely because the codec can append to such files. Authority comes from the active descriptor plus the backend’s fencing checks.

Ledger and query interfaces stay separate

ArrivalLedger owns custody operations. ArrivalQuery owns facts, ticks, folds, search, and SQL-oriented reads. A query handle MUST NOT expose a generic mutation escape hatch into the ledger. An implementation may share one database and transaction engine beneath both without sharing their authority surface.

04

The append transaction

Correctness depends on making head comparison, coordinate assignment, record insertion, and head advancement one indivisible transition for every accepted append. A backend MUST support one record and MAY advertise a larger atomic-record limit. A database transaction, file lock plus fsync, or service consensus step may implement it; the observable result is the same.

  1. Fence the lineage. Acquire the backend’s serialization primitive for this lineage.
  2. Read and verify the actual head. Validate the adopted head record rather than trusting cached metadata alone.
  3. Compare all head fields. Lineage, ordinal, and record hash must match the request.
  4. Validate drafts. Recheck grammar, body profile, admission decision, signatures required by policy, and configured limits.
  5. Assign custody. Generate successive ordinals, predecessor links, and record hashes inside the fence.
  6. Persist the accepted unit. Insert every record in the request plus any required recovery metadata atomically; refuse before mutation when the request exceeds the backend’s limit.
  7. Advance the head. Update the authoritative head to the final inserted record in the same atomic transition.
  8. Establish durability. Do not report success until the declared durability profile is satisfied.
append succeeds ⇔ actual_head == expected_head ∧ durable(all assigned records)

Atomic groups versus batch records

A backend with an atomic limit above one can append several ledger records in one transaction for import efficiency. A backend whose safe limit is one remains conforming and imports by verified single-record steps. A batch record is different: it expresses one application ceremony whose multiple fact rows share one ordinal. Backend batching must not rewrite one semantic batch into several fact records or vice versa.

Network retries

A remote Authority SHOULD support an opaque idempotency key scoped to the lineage and authenticated caller. Repeating the same key and request returns the original commit; reusing it with different content refuses. The mapping is backend metadata, not a ledger field. Without that capability, a lost response produces an “outcome unknown” result and the caller reconciles by reading the expected successor and its authored content commitment before deciding whether to retry.

Typed refusals

The failure conditions this contract names — head mismatch, same-height fork, unknown backend, atomic limit exceeded, and not-authority — surface as typed refusals under one backend-neutral root, so a caller catches a refusal without knowing which adapter produced it. A capability a backend deliberately does not offer is typed NotSupported under that same root: an absence capabilities() already reports is a contract answer, not a fault. Every other failure is backend-specific BY DESIGN. The root covers exactly what the contract text asserts and no more, because an adapter that lumped its own faults into these would be making a claim the contract cannot back (decision:design/arrival-slice2-contract-text, ruling 2).

05

Durability and failure semantics

“Durable” is meaningless without a failure boundary. Every Authority reports a named profile and its limits; callers may require a stronger profile than a backend offers.

ProfileSuccessful append survivesTypical mechanism
ProcessProcess failureKernel-persisted local write; not sufficient for canonical use by default
HostProcess and host restart / power loss under storage guaranteesFile or database sync through durable local media
ReplicatedLoss of one declared failure domainSynchronous database or service replication
ArchiveImmutable-object retention policyContent digest, versioning, retention lock, redundant objects

Crash outcomes

  • Before the atomic commit: no new complete record is visible.
  • After a confirmed commit: the entire accepted append unit is visible and the head names its last record.
  • When acknowledgment is lost: the client receives an unknown outcome and reconciles; it is not told the append failed.
  • A backend-specific torn staging fragment is never exposed as a complete logical record.
  • Recovery may discard only data proven never to have become a complete committed record under that backend’s protocol.
Capability scope matters

The current file adapter’s advisory flock contract is local POSIX storage. It must advertise that scope and refuse unsupported network filesystems; moving the same bytes onto NFS does not inherit safe multi-writer authority.

06

Reads and consistent snapshots

A reader first captures a head. Every subsequent operation through that head observes an immutable prefix, even while writers extend the lineage. Backends may implement this with MVCC, a read transaction, a bounded file range, or a versioned service token.

Required properties

  • Prefix consistency: a scan never mixes records from incompatible heads.
  • Deterministic order: results are ascending by ordinal, independent of physical row or page order.
  • Stable membership: a record returned at a coordinate recomputes to the hash committed by its successor or captured head.
  • No silent gaps: absence before the captured head is corruption, not end of stream.
  • Bounded paging: page tokens carry or bind to the captured head; ordinary row offsets are not portable continuation tokens.

Verification levels

LevelWorkClaim
OpenGenesis, stored head metadata, and adopted head recordThe backend can identify a self-consistent current tip.
IncrementalVerified checkpoint to captured headThe suffix follows a previously fully verified prefix.
FullGenesis through captured headGrammar, density, lineage, and hash chain are intact for the complete prefix.

Open-level checks are operational fast paths, not substitutes for full audit. A backend MUST describe exactly which level each API invokes.

Verification never repairs

A verify at any level MUST NOT mutate the ledger, its projections, or head metadata — no catch-up, no truncation, no rebuild of existing projection state, no head re-stamp. A backend whose ordinary open path performs recovery MUST offer verification a route that does not, because an operation that repairs on the way to reading has destroyed the evidence it was asked to judge and can only report an agreement it just manufactured. Materializing a projection that does not yet exist is not repair: it destroys no prior state and can hide no divergence. Repair belongs to open-time recovery and to explicit rebuild operations, which say so in their names. This generalizes §07’s rule that projection state is never used to repair canonical ledger history: neither direction of repair may travel under a verification verb (decision:design/arrival-slice2-contract-text, ruling 1).

07

Projections and query surfaces

Projection strategy is a capability choice, not part of the ledger’s physical contract. The same canonical record storage can support views, generated columns, selective indexes, asynchronously maintained materializations, or an external query database.

StrategyStorage costFreshnessRecovery
Direct record queryNo duplicate projection rowsAt captured headNo rebuild; query logic must understand bodies
Views / generated columnsMostly indexesAt captured headRecreate schema objects
Transactional materializationSelected duplicated fieldsAt commitRebuild deterministically from ledger
Asynchronous projectionSeparate query stateExplicit watermarkResume from verified projected head

Projection obligations

  • Every materialized row records or can derive (arrival_ordinal, arrival_seq).
  • Batch expansion order is deterministic and shared by live indexing and full rebuild.
  • The projection stores a verified projected_through head, not merely a row count.
  • Rows beyond, missing before, or inconsistent with that watermark cause refusal or rebuild.
  • Projection state is never used to “repair” canonical ledger history.
  • Query results report the lineage and projected prefix they actually represent.

A verified projected_through head is a claim the query surface cannot make alone: a projection knows the coordinate it reached, and only custody holds the record whose hash completes it. head_at(watermark) in §03 is that resolution — the ledger-side read a projection calls to turn its watermark into a verified head, so meeting this obligation never requires giving a query handle a route into custody (decision:design/arrival-slice2-contract-text, ruling 3).

DuckDB + Quack shape

The personal backend can keep one canonical arrival_records relation, expose Quack-friendly read views, and add only worthwhile indexes or materialized columns. No companion .arrival file is required. Quack-facing access is read-only with respect to ledger custody; writes use the admission API.

08

Replication, import, and export

Exact replication

A replica consumes pre-coordinated records. It verifies each record and atomically compares its current full head before inserting the exact suffix. It never assigns a new lineage, ordinal, predecessor, signature, or record hash. A conflicting same-height record is a fork and stops replication.

Portable import

Import targets a new empty replica or staged authority by default. Importing into a non-empty target requires exact prefix agreement through the target head. The importer then appends only the verified remainder. “Merge” that re-coordinates content is an admission operation into another lineage, not replication. Import is a procedure over the operations §03 names, not an operation of its own: the table gives it no row, and one backend’s import stays a convention until a second backend shows which of it is shared (decision:design/arrival-slice2-contract-text, ruling 4).

Contract debt — resumable import

Resumable import is required for conforming limited backends; the reference file backend does not yet implement it. A backend whose atomic limit is below the verified remainder cannot land that remainder in one step, so a single-shot importer refuses forever instead of progressing — §04 already says such a backend imports by verified single-record steps, and §12 exercises import among the configured limits. The importer that advances in bounded, resumable steps is therefore contract-implied, and it is a design rather than a fix: build it when a limited backend exists (decision:design/arrival-slice2-contract-text, ruling 5).

Canonical export

Export captures one head, scans its complete prefix in ordinal order, re-encodes each record with the selected wire codec, and writes a manifest. An implementation that stores typed columns MUST prove that the reconstructed logical JSON values reproduce every stored rh before claiming export success.

Replica is not authority

A successfully imported copy remains a replica. Letting it accept independent writes without re-custody creates a fork even if both copies began byte-identical.

09

Reference implementation shapes

File authority

JSONL + optional SQLite

The current ArrivalLog becomes an adapter. Local lock, append, flush/fsync, verified tail, deterministic scan; SQLite remains a projection.

Personal authority

DuckDB

Typed lineage and record relations, transactionally updated head, views or light materializations, one controlled writer, Quack-oriented reads.

Team authority

PostgreSQL

Lineage row lock or equivalent fence, unique coordinates, JSON semantic bodies, transactional head and projection work, admission service in front.

Cold replica

Object archive

Canonical stream plus manifest, immutable retention and redundant copies. Excellent witness evidence; intentionally incapable of assigning ordinals.

10

The backend as a migration target

The migration sidecar sees only a generic staged target. That is the simplification that makes a full break manageable: legacy-to-Arrival translation is written once; File, DuckDB, and PostgreSQL each implement the same sink.

Sidecar-facing seampseudocode
target = BackendRegistry.open(staging_descriptor)
head = target.mint(migration_genesis)

for group in legacy_source.groups():
    drafts = transform(group)
    commit = target.append(head, drafts)
    head = commit.after

target.verify(Full(through=head))
target.export(through=head, codec="arrival-jsonl-v1")
publish_descriptor_atomically(staging_descriptor)

Publication contract

  • The target is created at a staging location or namespace.
  • Ordinary application writers cannot address it during migration.
  • Verification compares stable source inventory to target logical records and projections.
  • A head witness is retained before cutover.
  • Publication atomically changes the authoritative descriptor, not every consumer independently.
  • The legacy source becomes read-only archival evidence and never resumes writes after successful cutover.
11

Administration and integrity boundaries

Backend permissions prevent ordinary clients from mutating canonical relations, but the backend administrator remains capable of physical changes. The contract therefore combines prevention, local detection, projection agreement, and external witnessing.

PreventLeast-privilege roles, read-only query endpoints, filesystem controls, transaction fencing, backups.
Detect local damageGrammar, unique coordinates, dense scan, predecessor links, record hashes, verified head metadata.
Detect projection editsRe-derive or compare materialized rows and their projected-through watermark against the ledger.
Detect rollback or rewriteCompare the presented history to a head retained outside the authority.

Logical state commitment

A backend may expose a convenience state digest over protocol version, lineage, head, and counts. It is quick to compare across implementations, but it does not replace the chain or witness. The head hash already commits the complete dense prefix; counts make operator reports and projection audits easier to interpret.

state = SHA-256( "arrival/state/v1\0" || JCS({ lineage, head, counts }) )
Administrator deletion

Deleting a canonical record creates a gap or broken chain. Deleting only a projected fact creates ledger/projection disagreement. Deleting the tail leaves a valid shorter prefix, so detection requires the external head defined by the Witness Protocol.

12

Conformance suite and capability report

Executable gates

  • Run one golden record corpus through every adapter and compare canonical export bytes.
  • Race two writers at one expected head; exactly one commit wins.
  • Inject a failure at every append stage and prove no partial logical group is visible.
  • Lose an acknowledgment and verify idempotent replay or explicit reconciliation behavior.
  • Replace head metadata, delete interior and tail records, and exercise every verification level.
  • Scan a captured prefix while another writer appends and prove snapshot consistency.
  • Rebuild projections after permuting physical row order; compare rows and watermarks.
  • Export, import into another backend, export again, and require byte-identical wire output.
  • Exercise configured record, batch, nesting, import, and decompression limits.
  • Compare to a retained witness head for rollback and same-height fork detection.

Capability report

capabilities() returns machine-readable protocol and wire versions, supported profiles, maximum atomic append size, writer concurrency scope, snapshot semantics, durability profile, verification levels, query watermark behavior, idempotency support, export codecs, and configured resource limits. Deployment tooling refuses an Authority assignment whose required guarantees are absent.

First implementation sequence

Extract the current file behavior behind this interface first, preserving its tests. Build the DuckDB adapter second and use cross-backend export as the conformance oracle. Add PostgreSQL only after the contract has survived those two materially different storage engines. A git-hosted file-backend profile — fast-forward-only push as compare-and-append, checkout as a replica at a captured head — is seeded as the Replica/Archive-side forcing consumer (thread:track-jsonl-store-for-worktree-parity).
